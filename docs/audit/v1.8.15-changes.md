## 1. RG-16-01（P1）スクロールできる祖先があるだけで、到達範囲の検査をやめていた

### 何が起きていたか

`overflow` が `auto` / `scroll` の祖先が1つでもあると、「中身はスクロールで読めるはず」として**画面・文書との交差の検査を丸ごと省いて**いました。実際に動かせる向きも量も見ていません。

| 見本 | 語の位置 | どうスクロールしても出せたか | 前方の印 | 後方の読める語の印 |
|---|---:|---|---:|---:|
| `overflow:auto` の中の `position:fixed; left:-10000px` | x = −9,984 | **出せない** | **1** ❌ | 0 |
| `overflow:auto` の中の `position:absolute; left:-10000px` | x = −9,983 | **出せない** | **1** ❌ | 0 |
| ［対照］右へスクロールすれば読める語 | x = 417 | 出せる | 1 ○ | 0 |

入れ物は幅 100px に対して中身 300px しかなく、**左向きには 1px も動かせません**。画面へ出せない語に印が付き、`Tab` で止まれる点（x = −9,916）まで残っていました。

### どう直したか

`ownClips` が「スクロールできるか（真偽）」ではなく、**動かせる範囲そのもの**を返します。

```js
const rx = scrolls(cs.overflowX) ? Math.max(0, el.scrollWidth - el.clientWidth) : Infinity;
const ry = scrolls(cs.overflowY) ? Math.max(0, el.scrollHeight - el.clientHeight) : Infinity;
reach = { x1: b.x1 - rx, y1: b.y1 - ry, x2: b.x2 + rx, y2: b.y2 + ry };
```

- 動かせる**向き**は書字方向（LTR / RTL）で符号が変わります。そこは判別せず**両側へ同じだけ広げます**——広く見積もる＝読める側へ倒すためです
- 範囲は**いちばん内側の入れ物**で決めます。外側と重ねてはいけません（高さ 100px の入れ物に 5,000px の中身がある場合、中身は文書の高さを増やさないので、文書側の範囲と重ねると読める中身まで落ちます）
- ただし**入れ物そのものが文書のどこにも出せない**なら、中身も出せないものとして扱います

絶対・固定配置が包含ブロックでない祖先から逃げる規則は、`overflow` と同じくこの範囲にも適用します（逃げた先では、文書または画面との交差で決まります）。

### 直したあと

4件とも画素・到達可能性・印が一致し、画面の外の `Tab` 停止点は **0件**になりました。

## 2. RG-16-02（P1）角丸の used value が仕様と違っていた

### 何が起きていたか

`inset(... round …)` の半径で、**`/` が無いときに水平の px 値をそのまま垂直へ写して**いました。百分率は**軸ごとに基準が違います**（水平は幅・垂直は高さ）。また、隣り合う角の半径の和が辺の長さを超えたときの**比例縮小**をしていませんでした。

| 見本 | 語の画素 | 前方の印 | 後方の印 |
|---|---:|---:|---:|
| 200×50px の `inset(0 round 50%)` の中の語 | **12** | **0** ❌ | 1 |
| 100×50px の `inset(0 round 80px 80px 0 0)` の中の語 | **17** | **0** ❌ | 1 |

読める語に説明が付かず、後ろの同じ語だけが説明されていました。

### どう直したか

```js
const hx = expand(sides[0], w);
const vy = expand(sides.length === 2 ? sides[1] : sides[0], h);   // 同じ文字列を高さ基準で解き直す
...
let f = 1;
const limit = (sum, len) => { if (sum > 0 && len / sum < f) f = len / sum; };
limit(radii[0].rx + radii[1].rx, w);   // 上辺
limit(radii[3].rx + radii[2].rx, w);   // 下辺
limit(radii[0].ry + radii[3].ry, h);   // 左辺
limit(radii[1].ry + radii[2].ry, h);   // 右辺
if (f < 1) for (const c of radii) { c.rx *= f; c.ry *= f; }
```

CSS Backgrounds 3 の overlapping curves と同じく、**すべての半径へ同じ係数**を掛けます。あわせて `rectHitsRounded` の「角ごとに辺の長さで頭打ちにする」処理をやめました（比例縮小した形と食い違うため）。

## 3. RG-16-03（P1）回転・拡大縮小した切り抜きを、軸に沿った形として判定していた

### 何が起きていたか

平行移動でない変形があるとき、参照ボックスを `getBoundingClientRect()` の**外接矩形へ広げ**、円・楕円も viewport の軸に沿ったまま判定していました。切り抜きの形は要素の座標で定義され、**要素と一緒に回ります**。

| 見本 | 語の画素 | 前方の印 | 後方の印 |
|---|---:|---:|---:|
| `rotate(35deg)` ＋ `ellipse(50px 20px at 60px 60px)` の**外**の語 | **0** | **1** ❌ | 0 |
| ［対照］同じ形の**内**の語 | 33 | 1 ○ | 0 |

### どう直したか

形を**変形前の座標**で解き、**語の矩形のほうを変形前へ戻して**当てます。

変形の**線形部分**（回転・拡大縮小・傾き）は祖先から掛け合わせれば分かります。平行移動は解く必要がありません——`transform-origin` は平行移動しか生まないので、線形部分には効かないからです。平行移動ぶんは、線形部分で写した箱の外接矩形が `getBoundingClientRect()` と一致することから逆算できます（平行移動は外接矩形の形を変えないので、この1点で決まります）。

```js
const tx = border.left - Math.min(...xs), ty = border.top - Math.min(...ys);
```

- 変形前の箱の寸法は、計算後のスタイル（`width` / `height` ＋ padding ＋ border）から取ります。`getBoundingClientRect()` は変形後の値なので使えません
- 語の矩形は4隅を逆写像し、その**外接矩形**で当てます（広く見積もる＝読める側へ倒す）
- `matrix3d` / `perspective` は解かず、**形の判定そのものをしません**（可視へ倒す）
- 変形が恒等なら、以前と同じ経路をそのまま通ります（既存 218 件は無変更で通過）

## 4. RG-16-04（P1）文字が描かれているかの判定が、3つの経路を見ていなかった

### 何が起きていたか

塗り（`color` / `-webkit-text-fill-color`）の透明さと、縁取りの**幅**だけを見ていました。

| 見本 | 語の画素 | 前方の印 | 後方の印 |
|---|---:|---:|---:|
| 幅はあるが**色が透明**な縁取り | **0** | **1** ❌ | 0 |
| 透明な塗り ＋ `text-shadow: 0 0 0 black` | **202** | **0** ❌ | 1 |
| 透明な塗り ＋ `background-clip: text` | **270** | **0** ❌ | 1 |
| ［対照］黒い縁取り | 475 | 1 ○ | 0 |

読めない語に印が付き、読める語には付かない——両方向の誤りが出ていました。

### どう直したか

```js
const sw = parseFloat(cs.webkitTextStrokeWidth || '0');
if (sw > 0 && !TRANSPARENT.test(cs.webkitTextStrokeColor || '')) return false;  // 縁取りは幅と色の両方
if (cs.textShadow && cs.textShadow !== 'none') return false;                    // 影は文字の形を描く
if ((cs.backgroundClip || cs.webkitBackgroundClip) === 'text') return false;    // 背景の文字型の抜き
return true;
```

「どの経路でも描かれない」と言えるときだけ不可視と断定します。

## 5. RG-16-05（P2）`filter` の並び順を見ていなかった

`filter` の関数は**前から順に**適用され、後段の `url()` は前段の出力とは別の入力から新しい絵を作れます。「どこかに `opacity(0)` があれば消えている」と断定していました。

| 見本 | 語の画素 | 前方の印 | 後方の印 |
|---|---:|---:|---:|
| `filter: opacity(0) url("#flood")` | **1,260** | **0** ❌ | 1 |
| ［対照］`filter: opacity(0)` だけ | 0 | 0 ○ | 1 |

並びを関数ごとに切り出し、`opacity(0)` の**後ろに `url()` が1つも無い**ときだけ断定します（ぼかし・明度などは透明な入力を透明のまま返します）。

## 6. RG-16-06（P2）レイヤー名と class 名をページと共有していた

### 何が起きていたか

3通りを再現しました。

**① ページが `@layer repogloss` を使っている場合**——レイヤーの順序は**名前が最初に宣言された場所**で決まるため、ページ自身の規則がこちらのレイヤーへ合流し、後ろの `repogloss-scope` に負けます。

| | 起動前 | 起動後 |
|---|---|---|
| `display` | `grid` | **`block`** ❌ |
| `position` | `relative` | **`static`** ❌ |
| `z-index` | `5` | **`auto`** ❌ |
| `color` | 赤 | **黒** ❌ |
| 寸法 | 140×30px | **740×24px** ❌ |

**② ページの `<html class="iiyaku-off">` を消していた**——起動時に `class` を書き換えていたため、ページの class とそれに紐づく見た目（背景色）が失われました。

| | 起動後（v1.8.14） |
|---|---|
| `<html>` の class | **`""`**（消えた）❌ |
| body の背景 | **`transparent`**（`rgb(0,170,85)` が失われた）❌ |

**③ 指摘の「先行 layer 宣言で最大 z-index の固定 UI が漏れる」は、私の実測では起動後には再現しませんでした。** ページが `@layer repogloss-scope, repogloss;` を先に宣言した見本で、起動後は `position: fixed → static` / `z-index: 2147483647 → auto` と、絞り込みの規則が正しく効いていました。再現したのは**こちらの JS が走り出すまでの短いあいだ**の漏れで、これはレイヤーの順序と関係なく（対照でも）起きます。原因は同じ「名前の共有」なので、同じ修正で塞がります。

### どう直したか

- **レイヤー名**を `repogloss` / `repogloss-scope` から `repogloss-e7b41d` / `repogloss-e7b41d-scope` へ。両方の名前を `styles.css` の先頭で宣言するのは変えていません（そうするとページ側のレイヤーは必ず後ろに並び、ページが勝ちます）
- **OFF の目印**を `<html>` の class から、読み込みごとに変わる合言葉を値に持つ属性（`data-iiyaku-off="iiyaku-xxxxxxxx"`）へ。規則は `styles.css` から外し、走り出しに足す側（`ownStyleRules`）で組み立てます。**ページの class は読みも書きもしません**

**防げるのは「偶然のぶつかり」までです。** 公開リポジトリなので名前は誰でも読めます。狙って合わせられた場合と、配布 CSS が固定の class 名で書かれているために起きる**走り出しまでの短い漏れ**は、`DESIGN.md` の既知の限界に書きました。

## 8. RG-16-08（P2）名札を全部消された複製が、見えない Tab の停止点として残っていた

### 何が起きていたか

複製から `data-iiyaku-*` と `aria-label` を全部消すと、こちらの見分け方（**名札が2つ以上そろっているか**）を抜けられました。

```json
{ "属性": { "class": "iiyaku-icon", "role": "button", "aria-expanded": "false", "tabindex": "0" },
  "矩形": [66.2, 111.7, 0, 15], "実Tabで止まった": true }
```

CDP で実際に `Tab` を押すと、**0×0 の要素へフォーカスが移りました**。これは v1.8.14 では「既知の限界」として書いていたものです。

### どう直したか

**数え上げの当て推量をやめました。** 自分が作る要素（印・吹き出し・切替ボタン）へ、読み込みごとに変わる合言葉を **class としても**付けます。class は `cloneNode` でそのまま複製されるので、属性を全部消された複製でも捕まります。そしてページ側の持ち物がこの class を名乗ることはありません（値は毎回変わり、ページからは読めない隔離された世界で決めています）。

```js
for (const el of pick('.' + CSS.escape(UID))) {
  if (ownedIcons.has(el) || isOurChrome(el)) continue;
  if (el.getAttribute('data-iiyaku-owner') === UID) continue;   // ① で扱った
  if (hasPageContent(el)) continue;   // ページが中身を入れた節点は壊さない
  stripOwnIdentity(el);
}
```

第14回 RG-14-04 の「ページ所有の要素を壊さない」という条件は保たれます——**その要素はこの合言葉を持ちません**。合言葉の class も `stripOwnIdentity` で外します。

### 直したあと

複製の属性は `class=""` だけになり、実際の `Tab` は止まりません。

## 9. RG-16-09（P2）カーソルが動くたび、控え全体の見え方を問い直していた

### 実測（指摘とは規模が違いました）

指摘は「5,000候補・10移動で 70,000回」ですが、合図（`pointerover` / `pointerout`）は**要素の境目でしか出ない**ため、10回の移動でも見直しは2回分（**10,002回**）でした。**候補数に比例して増えること自体は事実**なので直しています。

### どう直したか

`checkVisibility()` の答えを、**1回のまとめ直しのあいだ覚える**ようにしました（積み上げた切り取りの覚え方と同じ前提に乗っています）。隠れた入れ物の中に何語も入っているページで効きます。

| 控えの候補数 | v1.8.14 | v1.8.15 | 削減 |
|---:|---:|---:|---:|
| 500 | 2,004 回 | **501 回** | −75% |
| 2,000 | 8,006 回 | **4,004 回** | −50% |
| 5,000 | 20,014 回 | **10,010 回** | −50% |

初回走査も速くなりました（中央値 27.9 → 20.6 ms・4組とも新版が速い・実行順は交互に反転）。

### 直していないこと

**候補数への比例は残っています。** 指摘は「カーソルの下の枝に関わる候補だけを索引化する」ことを勧めていますが、`:has()` や兄弟結合子を使えば**カーソルの位置と無関係な場所の見え方も変わりうる**ため、範囲を狭めるのは安全ではありません（狭めると、第15回 RG-15-07 で直した「短時間ひらくメニュー」を取りこぼす経路ができます）。**範囲ではなく1件あたりの費用を下げる**という直し方を選びました。
