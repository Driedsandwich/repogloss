## 1. RG-17-01（P1）スクロールの可動域を、両側へ対称に見積もっていた

### 何が起きていたか

v1.8.15 は「動かせる量」を `scrollWidth - clientWidth` から出し、**両側へ同じだけ**広げていました。しかし**スクロールの原点は片側にあります**。

| 見本 | `scrollLeft` の可動域 | 入れ物へ入れられるか | 印 |
|---|---|---|---:|
| 横書き左→右・`left:-150px` | **0 〜 200** | **入れられない** | 1 ❌ |
| 右→左（`dir="rtl"`）・`right:-150px` | **−200 〜 0** | **入れられない** | 1 ❌ |
| ［対照］右→左・`right:150px` | −200 〜 0 | 入れられる | 1 ○ |
| ［対照］左→右・`left:250px` | 0 〜 300 | 入れられる | 1 ○ |

どちらの向きでも、**原点より手前**には1pxも動かせません。画面へ出せない語に印が付き、`Tab` で止まれる点が残っていました。

### どう直したか

軸ごとに**実際の可動域**を出し、そこから届く範囲を計算します。

```js
function scrollRange(el, cs, axis) {
  const span = ...;                 // scrollWidth - clientWidth など
  const now  = ...;                 // いまの scrollLeft / scrollTop
  if (span === 0) return { min: now, max: now, now };
  if (now < 0)    return { min: -span, max: 0, now };   // 符号だけで原点が決まる
  if (now > 0)    return { min: 0, max: span, now };
  const backwards = axis === 'x'
    && (cs.direction === 'rtl' || /^(vertical-rl|sideways-rl)$/.test(cs.writingMode));
  return backwards ? { min: -span, max: 0, now } : { min: 0, max: span, now };
}
```

`scrollLeft` を δ 増やすと中身は δ ぶん**左**へ動くので、届く範囲は
`x1 = 切り取り線の左 + (下限 − いまの値)` / `x2 = 右 + (上限 − いまの値)` です。

**可動域の符号は実測で確かめました**——`dir="rtl"` は `[-200, 0]`、`writing-mode: vertical-rl` は横が `[-215, 0]`・縦が `[0, 275]`。いまの値が 0 でなければ、その符号だけで原点の側が決まるので書字方向を見ません。

## 3. RG-17-03（P1）変形前の寸法が `box-sizing` と `zoom` を反映していなかった

v1.8.15 は変形前の箱を「計算後の `width` ＋ padding ＋ border」で復元していました。

**実測**（同じ指定で `box-sizing` だけ変える）:

| | `content-box` | `border-box` |
|---|---:|---:|
| 計算後の `width` | 120px | 120px |
| `offsetWidth`（border box） | 148 | **120** |
| 旧式の計算（width＋padding＋border） | 148 ✓ | **148** ❌ |

`border-box` では `width` に padding と border が既に入っているので、**二重に足していました**。また `zoom` は箱の寸法を変えず**描画だけ**を拡大するので、写像に入れないと矩形と食い違います（実測: `zoom:2` の 120px の箱は、計算後のスタイルでは 120px、矩形では 240px）。

| 見本 | 語の画素 | 印 |
|---|---:|---:|
| `box-sizing:border-box` ＋ `rotate(25deg)` ＋ `clip-path:content-box` | **0** | 1 ❌ |
| `zoom:2` ＋ `clip-path:content-box` の外 | **0** | 1 ❌ |
| ［対照］`zoom:2` の `content-box` の中 | 84 | 1 ○ |

寸法は `offsetWidth` / `offsetHeight`（border box そのもの・変形も `zoom` も掛からない生の値）から取り、`zoom` は線形部分へ掛けます（一様な拡大なので、変形との掛ける順序を気にしなくてよい）。

## 4. RG-17-04（P1）塗りを「指定の有無」と「先頭の層」で判定していた

| 見本 | 語の画素 | 印 |
|---|---:|---:|
| `text-shadow: 0 0 0 transparent`（完全に透明な影） | **0** | 1 ❌ |
| `background:none` ＋ `background-clip:text`（塗りが無い） | **0** | 1 ❌ |
| 透明な gradient ＋ 不透明な画像の**2層の** mask | **391** | 0 ❌ |
| ［対照］黒い影 | 197 | 1 ○ |
| ［対照］透明な gradient だけの mask | 0 | 0 ○ |

- **影**は色を見る。色を書いていない影（`text-shadow: 0 0 2px`）は `currentColor` なので、読める側へ倒して「描かれる」とします
- **背景の抜き**は、背景画像か背景色が実際に塗りを作るときだけ「描かれる」とします
- **覆い（mask）**は層の並びです。カンマで切って（`rgba(…)` や `url(…)` の中では切らない）、**すべての層が完全に透明**なときだけ不可視と断定します

## 5. RG-17-05（P2）固定名の目印を、値に関わらず書き換え・削除していた

ページが `<html data-iiyaku-off="page">` を持っていると、起動時にそれを消し、紐づく背景色まで失わせていました。

**⚠️ 最初の直しには穴があり、自分で足した対照が捕まえました。** 「消すのは自分が書いた値のときだけ」にしたのですが、**OFF にする側では上書き**していました。ON/OFF を往復する対照で落ちて気づきました。

いまは**名前ごと読み込みごとに変えます**（`data-iiyaku-xxxxxxxx-off`）。名前が重ならなければ、書く側でも消す側でも壊しようがありません。目印を使う規則は走り出しに足す側で組み立てます。

### 直していない部分（レイヤー名の意図的な衝突）

指摘のもう半分——「固定のレイヤー名をページが**狙って**先に宣言すると、順序を握られる」——は直していません。理由と残る影響:

- 名前を読み込みごとに変えるには、配布 CSS を**走り出しに注入する形へ作り替える**必要があります（静的な CSS ファイルには合言葉を書けないため）。`web_accessible_resources` の追加を伴う設計変更です
- 残る影響は**ページが自分の class と `data-iiyaku-owner` の両方を持つ要素を作った場合に限られます**（実測で確認）。それは「自分の印に見せかけた、ページ自身の要素」であり、ページはその見た目を自前の CSS でいくらでも作れます
- 偶然のぶつかりは、当てられない綴り（`repogloss-e7b41d`）で塞いであります

この判断と残る影響は `DESIGN.md` の既知の限界にも書きました。

## 6. RG-17-06（P2）合言葉の class まで消された複製が、停止点として残っていた

`data-iiyaku-*` と `aria-label` に加えて**合言葉の class まで**消すと、残るのは固定の class・`role`・`tabindex` だけになり、ページの持ち物と見分けられませんでした（実測: 実際に Tab で 0×0 の要素へフォーカスが移った）。

見分ける手がかりは1つだけ残ります——**別の持ち主を名乗っているか**。第14回 RG-14-04 で壊してしまったページの要素は `data-iiyaku-owner="page"` を持っていました。名乗りがある要素には触れず、**名乗りが無く・空で・押せて・自分の class を持つ `<sup>`** からだけ操作性を外します。

**これは断定ではなく割り切りです。** ページがこの形の要素を自分で作れば巻き込みます。ただし外すのは操作性だけで、対象は幅0で中身の無い要素に限られ、**この形の見えない停止点はページが自分だけでも作れます**。

## 7. RG-17-07（P2）カーソルの費用が候補数に比例したまま

### 前回の私の報告を訂正します

第16回の対応で「指摘の『5,000候補・10移動で 70,000回』は実測 10,002回だった」と書きましたが、それは**カーソルが同じ要素の中を動く見本**での値でした。合図（`pointerover` / `pointerout`）は要素の境目でしか出ないので、私の見本ではほとんど合図が出ていませんでした。

**要素の境目を毎回またぐ**動かし方にすると:

| 控えの候補数 | v1.8.15 | v1.8.16 | 削減 |
|---:|---:|---:|---:|
| 2,000 | 28,042 回 | **20,334 回** | −27% |
| 5,000 | **75,085 回** | **40,038 回** | **−47%** |

v1.8.15 の 75,085 回は、指摘の 65,000 回とほぼ一致します。**指摘の規模が正しく、私の見本が合図を出していませんでした。**

### どう直したか

見直す範囲を狭めるのは、`:has()` や兄弟結合子があるため安全ではありません（第15回 RG-15-07 で直した「短時間ひらくメニュー」を取りこぼす経路ができます）。代わりに**使ってよい時間に上限**を置きました。

```
直近2秒のうち、控えの見直しへ 200ms（10%）を超えて使ったら、
カーソルの合図では動かない。2秒ごとの確認は続くので、正しさは失われず遅れるだけ。
```

**これは「減らす仕組み」ではなく「使いすぎを止める仕組み」です。** 軽いページでは発動せず、費用は変わりません。**候補数への比例そのものは残ります**（既知の限界）。

## 8. RG-17-08（P2）変形に捕まった fixed を、画面固定として扱っていた

`transform` などを持つ祖先は `position:fixed` の包含ブロックになります。その場合、その要素は**画面には固定されず、文書のスクロールで動きます**。

| | v1.8.15 |
|---|---|
| 初期（`y = 1166`・文書の高さ 1720） | 印 **0** ❌ |
| 900px スクロール後（`y = 266`・画面内） | 印 **0** ❌ |
| 2秒の確認のあと | 印 1 |

画面に入ってからも、暇なときの確認まで説明が付きませんでした。

**捕まっているかは、上へ辿るときの逃げ方で分かります。** `mode === 'fixed'` で上っている途中に包含ブロックを作る要素があれば、その下の固定要素は捕まっています。画面へ固定されているものだけを `fixed` として数えるようにしました。

直したあとは**最初から**説明が付きます（文書のスクロールで届く範囲にあるため）。対照の「本当に画面へ固定された、画面外の語」はいまも落とします。
