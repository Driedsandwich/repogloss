## 1. RG-18-01（P1）到達範囲を1つの矩形へ潰していた

### 何が起きていたか

v1.8.16 は「いちばん内側のスクロール枠」だけを見て、届く範囲を1つの矩形にしていました。**入れ子**では、内側で動かせても外側の切り取り線を越えられないことがあります。また、**文書そのもの**の到達範囲は横書き左→右の式で出しており、**縦の向き**も書字方向で変わることを見ていませんでした。

| 見本 | 実測 | 印（v1.8.16） |
|---|---|---:|
| 動かせない外枠（`scrollWidth == clientWidth`）の中で、内枠が左へ100pxずれている | どう動かしても枠に**入らない**（`elementFromPoint` は BODY） | 1 ❌ |
| `<html dir="rtl">` の文書で、`right:1800px` に置いた語 | `scrollX = -1100` で**画面に入る** | 0 ❌ |
| `vertical-rl` ＋ `direction:rtl` の枠で、上側（`top:-150px`）に置いた語 | 上へ**動かせる**（`scrollTop` は −180〜0） | 0 ❌ |
| ［対照］外枠を動かせば入る語 | 入る | 1 ○ |

### どう直したか

**枠ごとに「箱と動かせる量」を持ち、内側から外側へ区間を伝播させます。**

内側の枠を動かすと中身だけが動き、外側の枠を動かすと内側の枠ごと動きます。そこで「内側から k 番目までの枠を動かした合計」を S_k と置くと、

- S_k は S_{k−1} に k 番目の可動量を足した範囲に入る
- 語が k 番目の枠に入る条件は S_k ∈ (箱の始点 − 語の終点, 箱の終点 − 語の始点)

となり、**内側から外側へ区間を狭めていくだけ**で答えが出ます（軸ごとに独立）。文書そのものも、まったく同じ形（箱＝画面、動かせる量＝文書のスクロール範囲）で最後に足します。

### スクロールの符号は、10通りを実測して規則にしました

| writing-mode | dir | scrollLeft | scrollTop |
|---|---|---|---|
| horizontal-tb | ltr | [0, s] | [0, s] |
| horizontal-tb | rtl | **[−s, 0]** | [0, s] |
| vertical-rl | ltr | **[−s, 0]** | [0, s] |
| vertical-rl | rtl | **[−s, 0]** | **[−s, 0]** |
| vertical-lr | ltr | [0, s] | [0, s] |
| vertical-lr | rtl | [0, s] | **[−s, 0]** |
| sideways-rl | ltr | **[−s, 0]** | [0, s] |
| sideways-rl | rtl | **[−s, 0]** | **[−s, 0]** |
| sideways-lr | ltr | [0, s] | **[−s, 0]** |
| sideways-lr | rtl | [0, s] | [0, s] |

規則は「横は、横書きなら `direction`、縦書きなら `rl` かどうか」「縦は、横書きなら常に正。`sideways-lr` だけ `ltr` で負、他の縦書きは `rtl` で負」。10通りすべてで一致します。いまの値が 0 でないときは、その符号だけで原点の側が決まるので書字方向を見ません。

## 3. RG-18-03（P1）変形の扱いが2つとも足りなかった

### ① 個別の変形プロパティを見ていなかった

`transform` だけを読んでいたため、`rotate: 35deg` のような**個別プロパティ**で回された切り抜きを、回っていないものとして判定していました。

CSS Transforms 2 の順序（translate → rotate → scale → offset → transform）で線形部分を合成します。平行移動は線形部分に効かないので見ません。`offset-path` に沿う回転と 3D は解かず、形の判定そのものをしません。

### ② 戻した矩形を広げすぎていた

`getClientRects()` が返すのは**回った箱の外接矩形**です。それを変形前へ戻すと、元より大きな平行四辺形になります。

実測（35°回転・元の箱は約 12×4）: 外接矩形は 13×11 → 戻すと約 **17×16** に膨らみ、形の外の語まで拾っていました。

**元の箱は復元できます。** 変形前の箱を w×h とすると外接矩形の寸法は

```
W = |a|·w + |c|·h
H = |b|·w + |d|·h
```

なので、この2式を解けば w と h が出ます（中心は、外接矩形の中心を戻した点と一致します）。ちょうど45°など `|a||d| = |b||c|` のときだけ解が定まらないので、そのときは平行四辺形で広く見積もります。

あわせて、**形との交差判定を矩形から多角形へ**変えました（`clipPolyToBox` / `polyHitsEllipse` / `polyHitsRounded`）。矩形で当てると、回った場所では必ず広がります。

| 見本 | 語の画素 | 印（v1.8.16） |
|---|---:|---:|
| `transform:rotate(35deg)` ＋ `ellipse()` の外 | **0** | 1 ❌ |
| `rotate:35deg`（個別プロパティ）＋ `ellipse()` の外 | **0** | 1 ❌ |
| ［対照］個別プロパティで回した形の**中** | 22 | 1 ○ |

## 5. RG-18-05（P1）`filter` を途中で打ち切り、`mask` の合成を見ていなかった

| 見本 | 語の画素 | 印（v1.8.16） |
|---|---:|---:|
| `filter: opacity(0) url(#f) opacity(0)` | **0** | 1 ❌ |
| 同じ不透明な層を2つ `mask-composite: exclude` | **0** | 1 ❌ |
| ［対照］`filter: opacity(0) url(#f)` | 1,260 | 1 ○ |
| ［対照］同じ2層を `add` | 445 | 1 ○ |

**`filter` は最後まで解きます。**

```
opacity(0) … そこで確実に 0 になる
url(...)   … 別の入力から描き直せるので、それまでの断定を捨てる
その他     … 透明な入力は透明のまま返す（断定は変わらない）
```

`opacity(0) url(#f) opacity(0)` → 0 → 捨てる → **0** なので消えていると言えます。`opacity(0) url(#f)` → 0 → 捨てる、なので消えているとは言いません。

**`mask` の合成（Porter-Duff）は解きません。** 足し合わせ以外は「**断定できない**」とします（→ §6）。

## 6. 断定できない候補で、その語を使い切らないようにしました

`mask` の合成のように解けない指定があるとき、v1.8.16 は「可視」と決めて印を付けていました。その結果、**画素0の語が「ページで最初の1回」を使い切り**、後ろの読める同じ語が説明されませんでした。

いまは**2周します**。

1. **1周目** … 確実に見える候補だけへ印を付ける。断定できない候補は見送り、その節点を控える
2. **2周目**（まとめ直しの最後） … 控えた節点のうち、**まだどこも引き受けていない語だけ**を、その候補で引き受け直す

こうすると、ページのどこかに確実に見える同じ語があれば必ずそちらが勝ち、どこにも無ければ元どおり印が付きます。2周目は「断定できない候補があったとき」だけ走ります。

## 7. RG-18-06（P2）**私が前の版で入れた割り切りが、ページの持ち物を壊していました**

v1.8.16 では「名乗りが無く・空で・押せて・自分の class を持つ `<sup>`」から操作性を外していました。第17回 RG-17-06（名札を全部消された複製が押せる点として残る）を塞ぐためです。

しかしこれは**形が同じだけの要素を、こちらの複製だと決めつける**やり方でした。

| | 起動前 | 起動後（v1.8.16） |
|---|---|---|
| ページが置いた `<sup class="iiyaku-icon" role="button" tabindex="0" aria-label="page control">` | そのまま | **`role`・`tabindex`・`aria-label` が消えた** ❌ |

**撤回しました。** 自分のものと断定できない要素には触れません。

その結果、**第17回 RG-17-06 は既知の限界へ戻ります**——見分けられない複製は、幅0で中身の無い、押せるだけの要素として残ります。ただし**その形の停止点は、ページが自分だけでも作れます**（こちらの class を使う必要がない）。構造として断つには、印を closed shadow root の中へ入れて複製できなくする必要があり、それは別の作り直しになります。

対応する受入条件も書き直しました。いま固定しているのは「**自分のものと断定できない要素には触れない**」で、複製が押せる点として残ることは**既知の限界として明示的に試験へ書いて**あります。

## 8. RG-18-07（P2）レイヤー名の意図的な衝突 — **直していません**

3巡続けての持ち越しです（第16回 RG-16-06 ③／第17回 RG-17-05 後半／第18回 RG-18-07）。

**実測した影響**: ページが `@layer repogloss-e7b41d-scope, repogloss-e7b41d;` を先に宣言し、その中で `.iiyaku-tooltip[data-iiyaku-owner]` を指定すると、こちらの絞り込みの規則が勝ってページの指定が消えます（`display: grid → block`、赤 → 黒、140×30px → 740×24px）。

**影響が及ぶ範囲**: ページが**自分の class と `data-iiyaku-owner` の両方を持つ要素**を作った場合に限られます（実測で確認）。それは「自分の印に見せかけたページ自身の要素」で、ページはその見た目を自前の CSS でも作れます。偶然のぶつかりは、当てられない綴りで塞いであります。

**直し方は分かっています**: 配布 CSS を**走り出しに注入する形へ作り替え**、選択子を読み込みごとに変わる合言葉で絞る（`[data-iiyaku-owner="<合言葉>"]`）。そうすると絞り込みの規則そのものが要らなくなり、この衝突も、第16回で残した「走り出しまでの短い漏れ」も同時に消えます。ただし `manifest.json` の `content_scripts.css` と配布ファイル一覧を触る変更で、**梱包の作り方が変わります**。5件の P1（見え方の判定の作り直し）と同じ回に混ぜると、取り違えたときの切り分けが難しくなるため、**別の回に単独で行う**判断をしました。

## 9. RG-18-08（P2）カーソルの費用

**何も見つからない見直しが続いたら、間隔を空ける**ようにしました（150ms → 最大 300ms）。メニューが開いて1つでも見つかれば即座に戻します。上限を 300ms に留めているのは、第15回 RG-15-07 で直した「短時間ひらくメニュー」を取りこぼさないためです。

要素の境目を毎回またぐ動かし方での、`Element.checkVisibility` の呼び出し回数（陽性対照＝1回で確認済み）:

| 控えの候補数 | またいだ回数 | v1.8.16 | v1.8.17 |
|---:|---:|---:|---:|
| 500 | 10 | 7,521 | **5,012** |
| 2,000 | 10 | 18,031 | 20,023 |
| 5,000 | 10 | 20,039 | 35,032 |
| 500 | 40 | 25,581 | **14,546**（−43%） |
| 2,000 | 40 | 68,119 | **58,083**（−15%） |
| 5,000 | 40 | 85,127 | 115,122（**+35%**） |

**5,000件では回数が増えました。** 1件あたりの判定が軽くなったぶん、同じ時間の予算（直近2秒のうち200ms）でより多く回るためです。**回数は費用の代わりになりません**——同じ実測で、40回またぐあいだ（約8秒）の余分な実時間は **224ms** でした。

**回数そのものは、またいだ回数に比例したままです。** 見直す範囲を狭めるのは `:has()` や兄弟結合子があるため安全でなく、間隔の上限も 300ms までしか伸ばせません。この限界は残ります。
