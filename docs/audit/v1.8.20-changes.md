## 1. RG-21-01（P1）URL の画像を、画素を見ずに断定していた

### 何が起きていたか

背景（`bgClipTextPaintsAt`）は、明示の寸法を持つ画像について「箱と語の矩形が交われば描かれる」としていました。`mask`（`maskLayerState`）も、断片でない URL は `alpha` / `match-source` なら残る側にしていました。**どちらも画像の中身（alpha）を見ていません。**

| 見本 | 語の画素 | 実測（v1.8.19） |
|---|---:|---|
| 完全に透明な 1×1 PNG を `background-clip:text` に `100% 100%` で敷く | **0** | 前方に印1・後方0 |
| 対照: 不透明な 1×1 PNG で同じことをする | 729 | 前方に印1・後方0（正しい） |
| 完全に透明な 1×1 PNG を `mask-image` に置く | **0** | 前方に印1・後方0。**印も0画素のまま Tab の順路に入った** |

### 直したこと

**gradient 以外の層は、背景も mask も断定しません。** 明示の寸法があることを「不透明である」ことの証拠にしません。中身を知るには読み込みが要り、それは新しい通信になります。

> **⚠️ 代償を明記します。** **不透明な画像で塗った／覆った語も、説明されなくなりました。** 既存の対照2件（第17回 RG-17-04 の「透明な層の後ろに画像の層がある mask」・第19回 RG-19-04 の「同じ画像を繰り返して覆う」）は、この版から**印を付けない**側の期待値へ変えています。gradient の対照は変わっていないので、繰り返しや寸法の判定そのものは生きています。
>
> `data:` の URL なら画素をほどけますが、canvas への描き出しと非同期の作り直しが要り、今回の8件と混ぜると切り分けられません。**次の候補**として残します。

## 2. RG-21-02（P1）背景の反復軸と origin を取り違えていた

2つ間違えていました。

| 見本 | 語の画素 | 実測（v1.8.19） | 向き |
|---|---:|---|---|
| `background-repeat: repeat-x` の背景を上端に置き、語は下方 | **0** | 前方に印1・後方0 | 見えない語を可視と誤答 |
| 層ごとの `background-origin: content-box, border-box` | **320** | 前方に印0・後方1 | 見える語を不可視と誤答 |

`no-repeat` を含まなければ「全面に届く」としていたため、`repeat-x`（横だけ）・`repeat-y`（縦だけ）を区別できていませんでした。`background-origin` は、他の層プロパティと違って**カンマ区切りの値全体**を1つの origin として扱っていました。

### 直したこと

`repeat` を **x / y の2軸へ正規化**します（`repeat-x` = 繰り返す／繰り返さない、`repeat-y` = その逆）。`space` と `round` は隙間や縮尺が絡むので**断定しません**。`background-origin` も `image / size / position / repeat / clip` と同じ層番号で取り出します。

## 3. RG-21-03（P1）祖先が最前面に出るのを、露出の証拠にしていた

v1.8.19 は `hit.contains(icon)`（＝当たり判定が印の**祖先**を返した場合）も「見えている」と数えていました。祖先の `::before` / `::after` が印を覆うと、`elementFromPoint` が返すのは**その祖先**なので、0画素の印が合格します。

| 見本 | 実測（v1.8.19） |
|---|---|
| 祖先の不透明な `::after`（`inset:0; z-index:999999`）が印を覆う | 印の5点すべてが**祖先**を返すのに、`tabIndex:0` のまま Tab の順路に入った |

### 直したこと

露出と数えるのは、**最前面が印そのものか、印の子孫**のときだけにしました。

> v1.8.19 で `hit.contains(icon)` を足したのは、「スクロールで送られた先にある印」の対照5件を守るためでした。**それを守るのは `visibleNow` の門のほう**で、覆いの判定は「いまスクロールを動かさずに見えている印」にだけ当てています。この版でもその5件は通っています。
>
> **⚠️ ここで私は1つ回り道をしました。** 監査の助言どおり `elementsFromPoint` の重なり順を見る形で書きましたが、**先頭要素は `elementFromPoint` と同じもの**で、この判定に足すものがありませんでした（実測の重なりは `[祖先(::after), 印, 祖先, BODY, HTML]`）。書き足したコードは削り、注記に実測を残しました。

> **⚠️ 既知の限界として残します。** `pointer-events: none` の要素が印を覆っている場合、当たり判定には出ないので検出できません。印自身が `pointer-events: none` にされた場合も同じです。どちらも**覆いを主張しない**側へ倒しています（→ `AUDIT.md` §7）。

## 4. RG-21-04（P2）CSSOM の変更を、規則の数だけで見ていた

| 見本 | 実測（v1.8.19） |
|---|---|
| 1つの規則の `selectorText` を、**規則数を変えずに** `:hover` の規則へ差し替える | 300ms・600ms で印0（2,400ms でようやく1） |

実測（同じ見本・修正後）: 差し替えから **320ms** で印が付き、自前 style は不透明度も幅も戻りました。

## 5. RG-21-05（P2）`:active` を購読せず、待たせた合図の相手を失っていた

`HOVERISH`（規則の走査）には `:active` が入っているのに、**購読する合図には入っていません**でした。さらに、間引きの窓で待たせた合図を、待ち時間のあとに**引数なしで**呼び直していたため、`pseudoStateKey` が相手の連なりを持たない別の鍵になっていました。`hoverPending` は宣言だけで**一度も true にならず**、入口の門も効いていませんでした。

| 見本 | 実測（v1.8.19） |
|---|---|
| `:active` だけで開くメニュー（先にカーソルを置いて `pointerover` を使い切ってから押す） | 押しているあいだ印0。**2,450ms** でようやく1 |
| 対照: `:hover` で開くメニュー | **320ms** で1 |

### 直したこと

`pointerdown` / `pointerup` / `pointercancel` を購読し、**押している相手の連なり**も擬似クラスの鍵に入れました（そうしないと「同じ場所を押した」が hover と同じ鍵になり、`doneStates` に阻まれます）。待たせた合図は**そのときの鍵のまま**処理し、予約した時点で `hoverPending` を立てます。

実測（修正後）: `:active` のメニューが **320ms** で付きます。

## 6. RG-21-06（P2）見分けられない複製 — **閉じました**

第19回から3巡持ち越していたものです。**単独で押せる印を、closed shadow root の中の `<button>` へ移しました。**

```html
<span class="iiyaku-icon …" data-iiyaku-owner="…">   ← light DOM の host。role も tabindex も持たない
  #shadow-root (closed)
    <button aria-label="「branch」の解説" aria-expanded="false" aria-describedby="iiyaku-desc">
    <span id="iiyaku-desc" hidden>日本語の説明全文</span>
    <slot>
```

### なぜこれで閉じるか（すべて実測・Chrome 151）

| 何を | 実測 |
|---|---|
| `cloneNode(true)` が shadow root を複製するか | **しない**（複製された host は空・押せる要素0） |
| ページから `host.shadowRoot` | **`null`**（closed なので取れない） |
| ページの `document.querySelectorAll('button')` | shadow の中の button を**見つけない** |
| `document.elementFromPoint` | **host へ retarget される**（＝印の実測はそのまま効く） |
| 全署名を消した複製の Tab 停止点 | **増えない**（実キーで数えて前後同数） |

**ページの持ち物には相変わらず触れていません。** 複製を書き換えるのではなく、**そもそも押せる点が生まれない形**にしました。ページが最初から持っている `<sup class="iiyaku-icon" role="button" tabindex="0">` は、まったく変えていません（対照で固定）。

### 進め方

第21回監査の移行設計に沿って、①単独の印だけを shadow へ ②host は `role` / `tabindex` を持たない ③E2E の `.iiyaku-icon` 直接参照を **host helper** と **CDP のアクセシビリティのツリー**へ ④複製の受入試験を固定、の順で進め、各段階で全試験を通しました。

意味づけはアクセシビリティのツリーで確かめています（実測）:

```
role=button  name="「branch」の解説"  expanded=false  focusable=true  ignored=false
description="同じ保管場所の中で作業の流れを枝分かれさせ、…"
```

### ⚠️ この作り直しで、私が3つ踏みました

| # | 何を間違えたか | どう気づいたか |
|---|---|---|
| 1 | **`<sup>` に `attachShadow` できない**（`NotSupportedError`）。host を `<span>` へ変えた | 書く前に実測した（`span` / `div` / `p` は可、`sup` / `i` / `b` / `small` は不可） |
| 2 | **`<slot>` を置かなかった。** shadow root を付けた要素は、`<slot>` が無いと light DOM の子を**描かなくなる** | 退役した印をページが本文の入れ物として使い回す既存試験が落ちた（`inside: 1` → `0`）。**ページの持ち物を壊していた** |
| 3 | **shadow 専用の CSS を、ページ側の `<style>` にも入れていた。** 裸の `button { … }` が入るので、**ページのあらゆるボタンを作り替えて**いた | こちらの切替ボタンの字形指定が落ちる既存試験が捕まえた。いまは `SHADOW_SECTION` をページ側から必ず外す |

⚠️ 試験の期待値も2つ間違えました。①`#prose` の印は1つと決め打ちしていた（実際は2つ・どちらも正しい）②「Tab で止まってから Enter で開く」と書いたが、実測では**Tab で止まった時点で開く**（`focusin` で出す仕様）。Enter はそこからの開閉の切り替えで、`preventDefault` が button の既定の活性化を止めるので二重には切り替わりません。

### 残る限界

- **装飾扱いの印**（入口に紐づくもの）は light DOM のままです。もともと `role` も `tabindex` も持たない非対話の要素なので、複製されても押せる点になりません
- `attachShadow` が使えない環境では、従来どおり light DOM の `role="button"` へ落ちます（内部定数 `USE_SHADOW_STANDALONE` で戻せます）

## 7. RG-21-07（P2）カーソルの合図ごとに、控え全件を測り直していた

`:hover` が変わるのは、動く前と動いた後の連なりの差だけで、それは両者の**いちばん近い共通の祖先**の中に収まります。`:has()` と兄弟結合子が無ければ、そこから外れた場所の見え方は変わりません。

**その範囲だけを測り直す**ようにしました。`:has()` や兄弟結合子を使う規則があるページ、stylesheet が変わった回は絞りません。**2秒ごとの確認は必ず全体を進めます**。

| 控えの候補数 | v1.8.19 | v1.8.20 |
|---:|---:|---:|
| 500 | 6,048 | **2,534**（−58%） |
| 2,000 | 24,048 | **12,036**（−50%） |
| 5,000 | 60,048 | **25,034**（−58%） |

v1.8.19 の値は、監査の独立実測（6,000／24,000／60,000）と一致しました。**比例そのものは残ります。**

> **⚠️ ここで私は2回間違えました。**
>
> ① **飲み込んだ合図の範囲を捨てていました。** `hoverPending` で見送った `pointerover`（＝新しく入った相手）の範囲が落ち、既存の対照が **8件**落ちました。**当たり判定を外した A/B**（11件 → 3件）で切り分けています。いまは範囲を合図ごとに広げて溜め、実際に走る直前に使います。
>
> ② **範囲の判定に、要素だけを通す `asElement` を使いました。** 控えに入っているのは**文字の節点**なので、絞った世代では全件が「範囲の外」になり、絞りが「全部飛ばす」に化けました。`:active` の反例が一度も拾えず、そこで気づきました。**このとき出した −67% という数字は誤りです**——同じ見本で v1.8.19 を測る対照を並べて確かめ直し、正しくは上表の −50〜−58% です。

## 10. 未検証として残っていること

- **Chrome 105〜150 の実機では試していません**（手元は 151 のみ）
- **画像（URL）の画素は解きません**——`data:` URL も含めて断定しません
- **SVG の `filter` と `<mask>` の中身は解きません**
- **`polygon()` / `path()` / `shape()` / `calc()` を含む形、3D の変形、`offset-path` も解きません**
- **変形前の矩形は、ちょうど45°など解の定まらない角度では断定しません**
- **一様でない `mask` は断定しません**
- **`background-repeat: space` / `round` は断定しません**
- **`pointer-events: none` の覆いは、当たり判定では見えません**（覆いを主張しない側へ倒す）
- **装飾扱いの印は light DOM のままです**（もともと押せる点ではない）。`attachShadow` が使えない環境では従来の形へ落ちます
- **カーソルの費用は、`:hover` を使う規則のあるページでは、またいだ回数に比例したままです**（絞っても2秒ごとの確認は全体を進めるため）
- **実サイトでの長時間の計測をしていません**（合成ページのみ）
- Developer Dashboard の実際の定義文。実スクリーンリーダーでの確認
