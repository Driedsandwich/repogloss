## 1. RG-23-01（P1）挿入を取り消す経路で、shadow の button を失効させていなかった

**直す前の最小の反例**（回答そのまま）: 前方の印だけ `opacity: 0 !important` にし、ページの MutationObserver が、引き取られた印の名札を外して本文の入れ物へ使い回す。v1.8.21 では、`#reused` の closed shadow の中に「「branch」の解説」の button が生きたまま残り、AX に **2個**・実 Tab で **1回** 止まった。登録済みの退役のあとも、使い回された host は `inline-flex`・左余白 4px・`middle` のままだった。

**直したこと**: 所有を手放す口を `relinquishIcon` の1か所にまとめ、登録済みの退役・登録前の取り消し・切断済みのどれでも、先に button を失効させてから所有の記録を消す。測る途中の例外も「描かれていない」として同じ口で引き取る。`:host` の装飾は、手放した root の `adoptedStyleSheets` からだけ共有の stylesheet を外す（共有の中身は変えない）。

**直した後**: 押せる解説 1・停止 0、host は `inline`・0px・`baseline`。
**対照**: observer が発火しない見本では、押せる解説 1・`#reused` 無し。現役の印の見た目は変わらない。
**試験**: 「第23回 RG-23-01: 挿入を取り消した印の中の button も失効させる」「第23回 RG-23-01: 使い回された host に、拡張の見た目を残さない」

## 2. RG-23-02（P1）通常の Tab フォーカスで、印とフォーカス枠が白地に消える

**直す前の最小の反例**: 白地・黒字のページで `start` から実 Tab で印へ。button の字・地・枠・outline が全部 `rgb(255,255,255)`、印の画素 0。hover でも button は白地に白で、light DOM の host だけが青地を描いた（「絵は shadow の中だけ」が hover で崩れていた）。reduced-motion でも中の button は遷移していた。

**直したこと**: 印の色（`--rg-ink`）と地の色（`--rg-ground`）を別の名前で持ち、hover / focus では地を印の色、"i" を地の色、outline を印の色で固定する。ダークの受け皿も light DOM 側とそろえ、shadow の中にも `prefers-reduced-motion` を置く。shadow のある印では、light DOM の host が hover / focus の地を描かない。

**直した後**: 実 Tab の画素 180・字と地が別の色・輪が見える。hover の host の地は透明。中の遷移 0s。
**対照**: ふつうの状態でも "i" と地が別の色で、フォーカスしていないのに輪は出ない。forced-colors（エミュレーション）でも実 Tab で止まった印の "i" が見える。
**試験**: 「第23回 RG-23-02: 実 Tab と hover で、印とフォーカスが見える（ライト）」「同（ダーク）」

## 3. RG-23-03（P1・一部実在）透明色の判定が `rgba(...)` に限られていた

**直す前の最小の反例**: `--fgColor-accent: color(srgb 0 0 0 / 0)` で、印は前方に残ったまま 0画素。
**一部実在の点**: 「`--rg-fg` を後から透明にすると鍵が変わらず塗り直さない」は、コード上は事実だったが、拡張全体では印が即座に作り直されて 104画素のまま（0画素の瞬間は観測されず）＝救われていた。

**直したこと**: 計算済みの色の alpha を読む `colorAlpha` に替え、読めない形は `null`。印の実測（`iconIsPainted`・`ensureShadowPaint`）では読めない形を「塗れている」と断定しない。塗り直しの鍵に `--rg-fg` / `--rg-bg` を入れ、hover / focus の "i" の色も測る。

**直した後**: 108画素。あとから透明にした場合も、作り直しではなく**同じ要素のまま**塗り直す。
**対照**: 第22回の形（`transparent`）は塗り直す。不透明な `color(srgb 1 0 0)` は塗り直さない（テーマに従う）。単体試験 `tests/color-alpha.test.js` も足した。
**試験**: 「第23回 RG-23-03: rgba 以外の書き方の透明でも、印は塗られる」

## 12. RG-23-12（P2）「1秒あたり 1,250 候補で頭打ち」は実装上の保証ではなかった

**誤りの中身**: 間隔は `min(2,000, max(400, 候補数 ÷ 1.25))` ms なので、控えが 2,500件を超えると1秒あたりに見る件数は再び増える。区切った続き（`scheduleLatentResume`）と暇なときの確認は、短い周期の入口の使いすぎの門（`overBudget`）を通らない。

**採った形**: 依頼どおり、**文書と注記を実装に合わせました**。`FAST_RATE` は「間隔を決める目安（1秒あたりの件数の上限ではない）」と注記し、AUDIT.md §4-1b・§7 #34 を実測に書き直しました。**実装の上限は変えていません**——一巡の時間を 1,250 件／秒に抑えると、20,000 件では一巡に最低 16 秒かかり、合図の出ない変化に気づくまでの遅れがその分延びるためです（回答の指摘どおり、両方は同時に保証できない）。

**実測**（Chrome 155・何もしない 10 秒・§13 の直した計測器・見本は見えない段落 N 件）:

| 控えの候補数 | 短い周期の間隔（式） | 全経路の `checkVisibility`／秒 | fast | idle | resume | 1回の最大 |
|---:|---:|---:|---:|---:|---:|---:|
| 500 | 400ms | **1,468** | 1,214 | 254 | 0 | 508 |
| 2,000 | 1,600ms | **2,207** | 1,198 | 1,004 | 5 | 2,008 |
| 5,000 | 2,000ms | **4,977** | 1,363 | 1,137 | 2,478 | 3,104 |
| 約 20,000（19,996） | 2,000ms | **13,662** | 1,267 | 1,248 | 11,147 | 3,536 |

**各候補の検出が終わるまでの最大時間**（実測）: CSSOM の `insertRule` で1語だけ見せ（DOM にも event にも出ない変化）、印が付くまでをページ側の時計で測った。見せる時刻を周期の中で 6 回ずらした最大:

## 13. RG-23-13（P2・一部実在）仕事量の計測が、fast と続きの経路を測っていなかった

### 計測器（`tests/e2e/timing-probe.js`）

以前は包んだ `queueMicrotask` の中だけを数えていた。いまは `setTimeout`・`requestIdleCallback`・`queueMicrotask` の予約のたびに「どの経路の中で予約されたか」を持ち越し、走った仕事をその経路へ付ける。fast・idle・resume の入口は、製品の予約する関数の最初の文（`fastTimer = null;` など）で見分け、見分けられなくなればその経路の回数が 0 のままになるので、試験の側で落とす。公表するもの: 経路ごとの回数・合計・最大・一巡の頭から入った回（`rg-paths`）、印を差し込んだ経路と場所（`rg-inserts`）、入口の予約が走った回数（`rg-ticks`）。

### 経路ごとの変異（使い捨ての worktree・1本ずつ）

`discoverLatent` に予算の引数を足し、**1経路だけ**予算を外した版を作って、試験「控えが多くても、1回の見直しを短く保ち…」と「第23回 RG-23-13: 経路ごとに、一巡の頭から入った見直しも刻まれている」を回した。

| 変異 | 旧い計測器（main の試験） | 直した計測器 | 落ちた検査の値 |
|---|---|---|---|
| なし | 通る | **通る**（7/7） | — |
| fast の刻みを外す | **通る**（見えていなかった） | **落ちる** | fast の1回 **20,000** 件 |

## 16. （自分で発見）Escape で閉じた吹き出しが出直す

**見つけた経緯**: 既存の E2E「単独の印は、closed shadow root の中の button が持つ（第21回 RG-21-06）」の小試験「Tab で印に止まると開き、Enter で開閉し、Escape で閉じる（実キー送信）」が、手元の Chrome 155.0.8059.80 では**タグ v1.8.21 の製品でも落ちた**（`Escape で閉じない`・expected 0 actual 1）。v1.8.21 の CI（2026-08-16）では通っていた。

**原因**（ページの世界で記録）: 最初の Escape の keydown で吹き出しが消え（`tip-`）、約 75〜100ms 後に **同じ印へ focusout（`relatedTarget = null`・`document.hasFocus() = false`）→ window の blur → `visibilitychange` hidden → window の focus → focusin** が来る。focusin の処理が説明を出すので、吹き出しが出直していた（`tip+`）。2回目の Escape では起きない。⚠️ headless の Chrome 155 では、このあと `visibilityState` が hidden のまま残り、次のカーソルの入力が数秒遅れて届くこともあった（試験では Escape を最後に押す）。

**直したこと**: Escape の keydown で、そのときフォーカスのあった相手を覚え（`escClosedAt`）、**同じ相手へ戻っただけの focusin では出し直さない**。忘れるのは、別の要素へフォーカスが移ったとき（`relatedTarget` があるか、文書がフォーカスを保ったまま body へ移ったとき）・Escape 以外のキー・マウスで印に乗ったとき。Enter・Space・クリック・hover で明示的に開くのは妨げない。

| 小試験 | 直す前 | 直した後 |
|---|---|---|
| 既存: Tab で止まると開き、Enter で開閉し、Escape で閉じる | **落ちる** | 通る |
| Tab で止まって開き、Escape で閉じたら、200ms 後も 800ms 後も閉じたまま（フォーカスは印のまま） | **落ちる**（記録: `key tip+ key tip- win-blur win-focus tip+`） | 通る |
| 【対照】Escape の後でも、Enter で開ける | 通る | 通る |
| 【対照】Escape の後に別の要素へ Tab で移って Shift+Tab で戻れば、また focus で出る | 通る | 通る |
| 【対照】キーを押さずに（ページの `focus()` と CDP の `DOM.focus`）別の要素を経て戻っても、また出る | 通る | 通る |
| 【対照】Escape の後でも、マウスで印に乗れば出る | 通る | 通る |

**未確認**: headful の Chrome や、ウィンドウを離れて戻る操作（別のアプリへ切り替えて戻る）で同じ経路になるかは、実機で確かめていない（同じ「同じ相手への focusin」になるので、直した形で閉じたままになる見込み）。CI の Chrome でも起きるかは PR の CI で分かる。

**試験**: 「Escape で閉じた吹き出しは、同じ印へフォーカスが戻っただけでは出直さない（第23回の3群目）」
