## 1. 指摘ごとの対応

### RG-4-01 — 描画されていない先祖を入口と誤認（P1）

**何が起きていたか。** `resolvePlacement()` は、印を入れる場所から上へ `HOST_CANDIDATE` をたどり、見つけた先祖を `resolveTrigger(el, true)` に渡していました。この `true` は「描画されていることを確認済み」という意味で、`canHoldFocus()` は `getComputedStyle()` と `getClientRects()` を呼ばずに即座に true を返していました。

根拠は「`isTarget()` が可視性を確認済み」でしたが、**`isTarget()` が見ているのはテキストノードの直接の親だけ**です。そこから上は別の要素なので、この一般化は成り立ちません。

**結果。** 次の3つを「到達できる」と誤判定していました。

| 反例 | v1.8.2 の判定 | 実際 |
|---|---|---|
| `display:contents` の `a[href]` | 到達できる | Tab 順路に入らない（`getClientRects().length === 0`） |
| `display:contents` の `button` | 到達できる | 同上 |
| `visibility:hidden` の先祖 ＋ 可視の子 | 到達できる | Tab 順路に入らない |

このとき印は `aria-hidden="true"` の装飾として置かれ、`role` も `tabindex` も持ちません。代わりの入口も無いため、**キーボードと一部の支援技術から説明へ到達できなくなります。**

**直し方。** `known` の伝播を廃止し、入口候補**自身**の描画状態を必ず確認します。速度は、走査1回のあいだだけ有効な `WeakMap`（`renderCache`）で同じ要素を測り直さないようにして回収しました。走査は同期的に走るため、その間に測定結果は変わりません。走査を抜けたら必ず捨てます（持ち越すと、GitHub が画面を差し替えた後に古い値で判定してしまうため）。

```js
// src/content.js
let renderCache = null;   // 走査1回のあいだだけ有効

function isRendered(el) {
  if (renderCache) {
    const hit = renderCache.get(el);
    if (hit !== undefined) return hit;
  }
  const cs = getComputedStyle(el);
  let ok = !(cs.display === 'none' || cs.visibility === 'hidden' || cs.visibility === 'collapse');
  if (ok && el.getClientRects().length === 0) ok = false;
  if (renderCache) renderCache.set(el, ok);
  return ok;
}
```

**確認**: E2E「到達できない場所には印を付けない（境界18件）」「描画されない入口は、ブラウザ自身も止まらない（反証の対照）」。後者は、`tabindex` の値の上では入口に見えること（`tabIndex === 0`）と、実際には箱が無いこと（`getClientRects().length === 0`）を両方確かめ、fixture が確かに反例になっていることを保証します。

### RG-4-02 — roving tabindex を構造だけで認定（P1）

**何が起きていたか。** `rovingEntry()` は、対応する role の composite container があり、同じ容器の中に `tabIndex === 0` の同種の項目があれば、`tabindex="-1"` の対象を到達可能とみなしていました。

しかし WAI-ARIA APG の roving tabindex は、**矢印キーへの応答として旧要素を `-1`、新要素を `0` にし、`element.focus()` で実際にフォーカスを移すアルゴリズム**を要求します。role・容器・0/-1 の静的な並びだけでは、そのアルゴリズムが実装されている保証になりません。

**直し方。** `rovingEntry()` と `COMPOSITE_OF` を削除し、`tabIndex < 0` は role や容器が何であっても入口にしないようにしました。

**この判断で何を失うかを、実サイトで測ってから決めました。** 指示書は3案（①注記しない ②`focusin` 後だけ登録 ③GitHub 固有部品に限定）を挙げていましたが、**①の損失が0件だったため、動的な状態を持ち込まない①を選びました。** 判定に状態が増えるほど、次の誤りが入りやすくなるためです。

測定は、配布ファイルだけを実際の Chrome に拡張として読み込み、出来上がった DOM を観測する方法です（判定式を再実装していません）。印が `aria-hidden` なら hosted とみなし、`data-iiyaku-for` から入口をたどって、その `tabIndex` を見ます。`-1` なら roving 経路にしか依存していない、という数え方です。

| ページ | 印 | roving 依存 | `readme` の入口 |
|---|---:|---:|---|
| `octocat/Hello-World` | 20 | **0** | `a.Link--primary`（tabIndex 0） |
| `k88hudson/git-flight-rules` | 41 | **0** | `a.Link--secondary`（tabIndex 0） |
| `octocat/Spoon-Knife`（ファイル一覧あり） | 14 | **0** | `li#README.md-item[role=treeitem]`（**tabIndex 0**） |
| `octocat/Hello-World/tree/master` | 20 | **0** | `a.Link--primary`（tabIndex 0） |

ファイル一覧が描画されていることも同時に確認しています（`role=tree` あり・`treeitem` 3件・tabIndex は `[0,-1,-1]`）。最初は既定のウィンドウ幅で測ったためファイル一覧が出ず、幅 1600px にして測り直しました。

**過去の記録の訂正。** 2026-08-05 に「`tabindex="-1"` の roving 項目を除外したら、ファイル一覧の `readme` の注記が丸ごと落ちた」と記録し、そこから「構造が揃っていれば到達可能とみなす」という規則を作りました。今回測り直したところ、**その因果は成り立ちません**。現在の GitHub では `readme` の入口は roving の「入口側」（`tabIndex === 0` の項目）に付いており、`-1` の項目ではありません。1度の観察から因果を確かめずに規則へ昇格させたことが、この指摘の原因です。

**確認**: E2E「矢印に応答する部品としない部品を、実キーで見分ける（対照）」。fixture に2つの tree を置いてあります。

- `#good-tree` — keydown ハンドラを実装した正しい部品。ArrowDown で移動し、ArrowUp で戻る
- `#nohandler-tree` — role も容器も `tabindex` の 0/-1 の並びも同じだが、**ハンドラが無い**。ArrowDown を送ってもフォーカスは動かない

どちらでも `-1` の項目には印を付けないこと、そして**壊れた側では実際に矢印が効かないこと**を、実キーを送って確かめます（fixture が反例になっていることの保証）。

### RG-4-03 — E2E の反例が足りず、oracle が独立でない（P1）

**何が抜けていたか。**

1. Shift+Tab を送っていない（前向きだけで「キーボードで到達できる」と書いていた）
2. ArrowUp を送っていない
3. 「構造は満たすが keydown ハンドラが無い composite」の反例が無い
4. 画面外のケースで `i.focus()` を直接呼んでおり、実際の Tab 移動を使っていない
5. roving の試験で `tree-entry.focus()` を先に呼んでおり、Tab で入口へ到達する過程を同じケースで証明していない

**直し方。** fixture に7ケース追加し、到達可能性の判定から対象への `.focus()` を外しました（開始位置の固定にだけ使います）。

追加した fixture:

### RG-4-05 — Windows E2E が非ゲート化（P1）

`.github/workflows/ci.yml` の Windows E2E step に `continue-on-error: true` が付いていました。GitHub Actions ではこの設定により、step の実結果が failure でも結論を success として継続できます。**Actions が緑でも「Windows E2E が成功した」ことにはなりません。**

**直し方。** `continue-on-error` を削除し、Chrome が見つからない場合も明示的に失敗させました。

```yaml
- name: Chrome の場所
  shell: pwsh
  run: |
    $p = "C:\Program Files\Google\Chrome\Application\chrome.exe"
    if (-not (Test-Path $p)) {
      Write-Error "Chrome が見つからない: $p"
      exit 1
    }
    Write-Output "found: $p"
- name: 拡張として読み込んでのテスト
  run: npm run test:e2e
```

**確認（受入条件そのもの）**: 使い捨ての PR で **Windows でだけ落ちる assertion** を1つ入れ、赤くなることを実測しました。

| | `e2e-windows` | 他7ジョブ | run 全体の結論 |
|---|---|---|---|
| わざと壊した検証用 PR | **failure** | success | **failure** |
| 対照（無傷の PR #11） | success | success | **success** |

Windows のログに `not ok 27 - 【一時】Windows のゲートが働くことの確認` が出ました。確認後、その PR は閉じてブランチをローカル・リモート両方から削除しています。

### RG-4-06 — OS 間比較と正本 ZIP の検証（P2）

**何が足りなかったか。** `package-hash` matrix は3 OS で合算ハッシュをログへ出すだけで、**値を集めて突き合わせる job がありませんでした**。「CI が OS 間で検証する」という記述は、workflow 上の機械的な処理としては実装されていない主張でした。また ZIP を作る仕組みが無く、手順書のままだったため、監査者が提出物を独立に照合できませんでした。

**直し方。**

1. `package-stage.mjs` が合算ハッシュを `dist/COMBINED_SHA256.txt` へ書く（ログを shell で切り出すと OS ごとに書き方が変わるため、ファイルにする）
2. `package-hash` が artifact として持ち出す
3. `hash-compare` job（`needs: package-hash`）が3件そろわない／値が割れると **exit 1**
4. `package:zip` / `package:verify-zip` を追加
5. `release-zip` job が ZIP を作り、検査し、artifact として持ち出す

**ZIP の読み書きは Node 標準の `zlib` だけで自作しました**（依存を増やさないため）。作るものが毎回1バイトも変わらないよう、日時を 1980-01-01 に固定し、並び順を配布一覧の順に固定し、追加の属性も入れていません。

`package:zip` は、配布対象に commit していない変更があると**警告ではなく終了コード 1 で止まります**。逃げ道は `--allow-uncommitted` だけで、その場合はファイル名に `UNCOMMITTED` が入るため提出物と取り違えません。

**検査で見ているもの**: 配布一覧との過不足0 ／ 1件ずつの中身が手元と1バイトも違わない ／ ZIP の中の version が一致 ／ 余分な親フォルダで包まれていない ／ 開発用・鍵らしきファイルの混入なし ／ 末尾に足されたごみが無い。

**検査そのものに判別力があることの確認**: [`tests/package.test.js`](../../tests/package.test.js) の**13件**で確かめています。うち**9件が「壊れたものを落とす」試験**、残り4件は対照です。**壊し方は、検査が持っている一覧の外側からも入れています**（一覧との突き合わせだけでは気づけない壊し方を含める）。

| # | 試験 | 期待 | 種別 |
|---:|---|---|---|
| 1 | 正しく作った ZIP | 通る | 対照 |
| 2 | 読み書きした中身が1バイトも変わらない | 変わらない | 対照 |
| 3 | 同じ中身から2回作る | 同じバイト列になる | 対照 |
| 4 | 余分なファイルを入れる | 落ちる | 破壊 |
| 5 | 開発用ファイル（`scripts/...`）を入れる | 落ちる | 破壊 |
| 6 | 鍵らしきファイル（`key.pem`）を入れる | 落ちる | 破壊 |
| 7 | ファイルを1つ減らす | 落ちる | 破壊 |
| 8 | ZIP の中の version を変える | 落ちる | 破壊 |
| 9 | 親フォルダで包む | 落ちる | 破壊 |
| 10 | 中身を1バイト書き換える | 落ちる（CRC ／ 本体と見出しの名前の食い違い） | 破壊 |
| 11 | 末尾にごみを足す | 落ちる（`unzip -t` は素通りさせる） | 破壊 |
| 12 | 先頭を切り詰める | 落ちる | 破壊 |
| 13 | 配布一覧そのものに配布禁止のものが載っていないか | 載っていない | 対照 |

**実装中に、自分の書き間違いを2件見つけました。**

1. **終端record（EOCD）で、中央ディレクトリの位置を14バイト目へ書いていた**（正しくは16）。自作の読み取り側が「中央ディレクトリの位置か大きさが合わない」で落ちたため気づけました。書き出しだけを作って「できた」で済ませていたら、壊れた ZIP を提出しかねませんでした。
2. **ファイル名が本体見出しと中央ディレクトリの2か所にあり、片方だけ書き換えられても素通りしていた。** 中央ディレクトリだけを読む実装だったためです。テストが1件落ち、原因を追ったら検査側の穴でした。両方を突き合わせるようにしています。

**独立した実装での確認**: 自作の読み書きは同じ作者なので、共通の思い込みを持ちうります。緩和として、Python の `zipfile` と `unzip -t`（いずれも無関係な実装）でも読めることを確認しています（13件・破損なし・手元のファイルと全件一致）。

### RG-4-07 — 既に複数形のキーの再複数形化（P2）

`buildPattern(keys)` が全辞書キーへ無条件に `pluralsOf()` を適用していたため、`actions` → `actionses` のような存在しない綴りを受け付けていました。

**該当は11件ではなく12件でした。** 辞書で `s` で終わるキーを数え直すと `request changes` も該当し、`request changeses` が作られていました。監査の一覧は単語1語のキーだけを拾っており、複合語のキーが漏れていました。指摘そのものは正しく、影響範囲がわずかに広かったものです。

**直し方。** 語末が `s` かどうかで機械的に決めることはしません（`status` のように `s` で終わる単数形があるため）。表示用のキーと、matcher が受け付ける綴り（surface forms）を分け、**明示的に列挙**します。

```js
// src/matcher.js
const ALREADY_PLURAL = new Set([
  'actions', 'checks', 'contributors', 'forks', 'insights', 'issues',
  'packages', 'projects', 'releases', 'request changes', 'stars', 'tags'
]);
const SINGULAR_ENDING_IN_S = new Set([]);   // 今の辞書には無いが、分類の枠は残す

function formsOf(key) {
  return ALREADY_PLURAL.has(key) ? [key] : pluralsOf(key);
}
```

**列挙漏れはテストが機械的に検出します。** 辞書に `s` で終わるキーが増えたのにどちらにも分類されていなければ落ち、分類表に辞書へ無いキーが残っていても落ちます。negative test は分類表から自動で作るので、キーが増えても書き足す必要がありません。

辞書の61概念と説明文は変更していません（キーの集合も説明文も v1.8.2 と完全に同一）。

`src/content.js` は①と②に、`STORE_LISTING.md` は④と⑤にまたがるため、中間状態を組み立てて分割しています。**分割後のツリーが分割前と1バイトも違わないことを17ファイル全件で突き合わせて確認済み**です。

## 3. 検証の再現方法

```sh
git checkout v1.8.3
npm test                     # 単体34件 + 構成107項目
npm run test:e2e             # 拡張として読み込む E2E 32件（Chrome と openssl が要る）
npm run package:stage        # 配布物を並べて合算ハッシュを出す
npm run package:verify       # 並べたものが今の中身と一致するか
npm run package:zip          # 提出用 ZIP を作って検査（SHA-256 が出る）
npm run package:verify-zip   # できた ZIP をもう一度検査
```

**テストに判別力があることを確かめる**（通るだけのテストは、何も見ていないテストと区別できないため）:

```sh
git show v1.8.2:src/content.js > src/content.js
npm run test:e2e             # → 32件中6件が落ちる
git checkout src/content.js

git show v1.8.2:src/matcher.js > src/matcher.js
npm test                     # → 単体21件中3件が落ちる
git checkout src/matcher.js
```

E2E には Google Chrome と `openssl` が必要です。Chrome の場所は `CHROME_PATH` で指定できます。`github.com` はローカルの HTTPS サーバへ向けるので、外部通信もアカウントも要りません。
