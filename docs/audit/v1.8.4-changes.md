## 1. 指摘ごとの対応

### RG-5-01 — 除外を決める前に、文字列を読んでいた（P1）

**何が起きていたか。** `isTarget()` は最初に `node.nodeValue` を取り出し、その後で `SKIP`（`contenteditable`・`textarea`・コード表示・`aria-hidden` など）を判定していた。印は入らず内容も変わらないが、**編集中のコメントや `textarea` の中身は、除外が決まる前に一度 JavaScript へ読み込まれていた。**

`PRIVACY.md` は編集領域を「読み取りも書き換えもしない」と書いていたので、実装と公開説明が食い違っていた。**「変更しない」と「読み取らない」は別のことである。**

**直し方。** 順序を入れ替え、`[inert]` も `SKIP` へ足した。

```text
handled か → 親要素があるか → SKIP に当たるか     ← ここまで文字列に触れない
      ↓
nodeValue を読む → 空白だけか → 辞書に当たるか → 実際に見えるか
```

**将来戻らないようにした。** `scripts/verify.mjs` が `isTarget` の本文を読み、`closest(SKIP)` の位置が `node.nodeValue` / `node.data` / `node.textContent` / `node.wholeText` のどれよりも前にあることを検査する。**v1.8.3 のコードを入れるとこの検査は落ちる**（実測: 「SKIP の位置=184 / 値を読む位置=15」）。

> **なぜ E2E ではなく静的検査か。** content script は隔離された世界で動くため、ページ側から `nodeValue` の getter を計装しても、拡張側の読み取りは観測できない。監査の独立プローブは content.js を直接ページへ流し込む方式なので計装できたが、**実際の拡張として読み込む E2E では同じ方法が使えない。** そこで順序そのものを機械で固定した。

### RG-5-02 — 見えない場所が「最初の1回」を使い切っていた（P1）

同じ語はページで最初の1回しか注記しない。**見えていない場所に印を付けると、その語はページのどこでも説明されなくなる。**

`isTarget()` の可視性判定はテキストの**直接の親**だけを見ていた。これでは足りない。手元の Chrome 151 で実測した結果:

| 隠し方 | 子の computed 値 | 子の箱 | 直接の親を見る判定 | `checkVisibility` |
|---|---|---|---|---|
| 祖先が `opacity: 0` | `opacity: 1`（継承しない） | rects=1・1264×24 | **見抜けない** | **false** ✅ |
| 祖先が `content-visibility: hidden` | 変化なし | rects=1・1264×24 | **見抜けない** | **false** ✅ |
| `inert` の中 | 変化なし | あり | **見抜けない** | true ❌ |
| 1px＋`clip`（読み上げ専用） | 変化なし | rects=1・1×1 | **見抜けない** | true ❌ |

**箱の有無では判別できない**のが要点。`getClientRects()` を見ても解決しない。

**直し方。**

1. `Element.checkVisibility({ opacityProperty, visibilityProperty })` を使う（祖先までまとめて見る）。古い Chrome 向けに `checkOpacity` / `checkVisibilityCSS` も一緒に渡す（知らない項目は無視される）
2. **`contentVisibilityAuto` は渡さない。** 渡すと `content-visibility: auto` の画面外要素まで false になり、長いページの下が永久に注記されなくなる（実測: 渡すと false、渡さないと true）。`verify.mjs` が渡していないことを検査する
3. `inert` は `SKIP` セレクタで、**文字列を読む前に**除外する
4. 1px＋`clip` は形で判定する（`isClipHidden`）。クラス名は版ごとに変わる自動生成なので名前では判定しない
5. 速度は走査単位の `WeakMap`（`visibleCache`）で回収する

**受入条件の実測**（E2E「見えていない場所には印を付けず、後ろの読める語へ付ける（4種）」）:

| 反例 | v1.8.3（隠れ側／後続） | v1.8.4（隠れ側／後続） |
|---|---|---|
| `inert` の中 | 1 / 0 | **0 / 1** |
| 祖先 `opacity:0` | 1 / 0 | **0 / 1** |
| 祖先 `content-visibility:hidden` | 1 / 0 | **0 / 1** |
| 1px＋`clip` | 1 / 0 | **0 / 1** |
| `content-visibility:auto` の画面外（壊してはいけない） | 2件注記 | **2件注記（維持）** |

fixture が本当に反例になっていることも、別の試験でブラウザ自身に確かめている（`checkVisibility` の戻り値と箱の数を見る）。**`content-visibility:hidden` は host 自身ではなく中身が隠れる**ので、対照は子要素で測る必要がある——最初 host で測って対照が落ち、そこで気づいた。

### RG-5-03 — 見えなくなった古い印が、後続を抑止していた（P1）

説明済みかの判定が `prev && prev.isConnected` だけだった。`isConnected` は **DOM に残っていることしか示さない。** 祖先が `display:none` になっても、`opacity:0` になっても、`inert` の中へ移されても true のままである。

実測（v1.8.3）: 注記済みの語を隠したあと、同じ語の可視ノードを追加しても、**新しい側に印が付かなかった**（0個）。

**直し方。** `usableGloss(key)` を追加し、次をすべて満たすときだけ「使える」と見なす。

```text
- DOM にあり、その場所が実際に見えている（isVisibleOccurrence）
- 単独の印なら、その印自身が Tab の順路に入る
- 装飾扱いの印なら、対応する入口が生きていて Tab の順路に入る
```

使えなければ `retireGloss(key)` で古い印を取り除いてから付け直す。印は `<sup>` 1つで中に文字を持たないため、取り除いても本文は壊れない。表示中の吹き出しがその印を参照していれば先に閉じる。

**受入条件の実測**（E2E「見えなくなった古い印は、後から現れた読める語を妨げない」）:

| | v1.8.3 | v1.8.4 |
|---|---|---|
| `display:none` にした後、新しい可視の同語 | 印 0 | **印 1** |
| `opacity:0` にした後、新しい可視の同語 | 印 0 | **印 1** |
| 隠された側に残る古い印 | 1 | **0** |
| ページ全体の同一キーの印 | 1（見えない方） | **1（見える方）** |

`verify.mjs` も `usableGloss` の存在と、`prev && prev.isConnected` が残っていないことを検査する。

### RG-5-05 — 綴りの機械生成が別語を拾っていた（P2）

`formsOf()` が、既に複数形として列挙したキー以外へ英語の複数形規則を一律に適用していた。61キーから **46の綴りを自動生成**しており、その中に意味の違う普通の英単語が入っていた。

実測で確認した誤一致: `securities`→`security`（金融商品）／`cis`→`ci`／`gits`→`git`／`mains`→`main`／`watchings`→`watching`／`visibilities`→`visibility`／`ci/cds`→`ci/cd`。

**直し方。** 生成をやめ、`EXTRA_FORMS`（キー → 受け付ける綴り）へ**明示的に列挙**した。判断の基準は2つ。

1. GitHub の画面か Git の文書に、その複数形が実際に出るか
2. 無関係な意味の普通の英単語と衝突しないか

2を満たさないものは、文法的に正しくても入れない。**46 の自動生成のうち 30 を残し、16 を落とした**（`approves` `blames` `cis` `ci/cds` `fetches` `gits` `mains` `origins` `pulls` `resets` `securities` `syncs` `upstreams` `visibilities` `watches` `watchings`）。

`lookupKey` も、語尾を落とす推測をやめて表の逆引きだけにした。

**テスト**: negative corpus 27件（監査の一覧＋こちらで足した一般語）が全件不一致。positive corpus 16件が全件維持。加えて「表に無い綴りが受け付けられていないこと（生成の復活の検出）」「1つの綴りが2つのキーへ割り当たらないこと」「辞書に無いキーが定義に残っていないこと」を機械的に検査する。**v1.8.3 の matcher を入れると5件落ちる。**

> `ci/cds` だけは扱いを分けた。綴りとしては拒否できている（`lookupKey('ci/cds') === null`）が、`/` が単語の区切りなので文字列の中の `CI` には当たる。そこに CI という語が実際にある以上これは誤りではないので、実際の挙動をテストで固定した。

### RG-5-06 — 提出候補の成果物が、必須ゲートに依存していなかった（P2）

`release-zip` が `needs: [verify, e2e]` だけだったため、**`e2e-windows` や `hash-compare` が落ちた実行からでも**「提出候補」という名前の成果物が出せた。また `pull_request` でも動くため、未マージの PR から同名の成果物ができた。

**直し方。**

```yaml
release-zip:
  needs: [verify, e2e, e2e-windows, hash-compare]
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

成果物に添える JSON へ、出どころと環境を足した。成果物だけが手元に残ったときに出どころを追えないと、提出物を取り違える。

```json
"source": { "repository": …, "commit": …, "ref": …, "workflowRunId": …,
            "workflowRunAttempt": …, "builtInCI": true },
"environment": { "node": "22.22.3", "zlib": "1.3.1-e00f703", "platform": "linux" }
```

`permissions: contents: read` と、すべての action の full SHA 固定は維持している。

## 4. 実装中に気づいたこと

**対照テストが自分の誤りを捕まえた。** 「反例が本当に見えないことをブラウザ自身に確かめる」試験を書いたとき、`content-visibility:hidden` の **host 自身**で `checkVisibility()` を測って落ちた。`content-visibility:hidden` が隠すのは**中身**なので、host 自身は描画されたままである。対照を子要素で測るよう直した。反例の側を測る試験が無ければ、この思い違いに気づかないまま「見えないことを確認した」と書いていた。

**`verify.mjs` の新しい検査が、自分のコメントに反応した。** 「`contentVisibilityAuto` を渡していない」検査が、`content.js` の**説明コメント**の中の語を拾って落ちた。コメントを除いた本体で判定するよう直し、本体に書いたら落ちることを対照で確かめた。
