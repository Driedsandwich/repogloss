## 1. 指摘ごとの対応

### RG-6-01 — 退役した印の元の語が、二度と注記されない（P1）

**何が起きていたか。** 印を入れるとき `splitText` でテキストを2つに割り、両方を `handled` へ入れている。v1.8.4 の `retireGloss` は `<sup>` を消すだけで、割れたテキストを `handled` から外していなかった。そのため、いったん退役した語は**そのページを開いている間ずっと説明されない**。

実測（v1.8.4・同じ DOM ノードでの往復）:

| 段階 | 元の場所 | 新しい場所 | 合計 |
|---|---:|---:|---:|
| 初期 | 1 | 0 | 1 |
| 元を隠し、読める場所に同じ語を出す | 0 | 1 | 1 |
| 読める場所を消し、元を戻す（`pushState` ＋ ノード追加） | **0** | 0 | **0** |
| 同じ要素を外して戻す | **0** | 0 | **0** |

**直し方。** 退役を可逆にした。自分が割った2つのテキストを1つに戻し、`handled` から外して走査対象へ返す。

```js
const prev = icon.previousSibling, next = icon.nextSibling;
icon.remove();
if (isText(prev) && isText(next)) {
  prev.appendData(next.nodeValue);   // 文字列は足し合わせるだけ。増減しない
  next.remove();
  handled.delete(prev);
}
```

**親全体へ `normalize()` は掛けない。** ページ側が持っている Text node の同一性や選択範囲を壊しうるので、触るのは自分が割った範囲だけにしてある。自分の DOM 操作で無限ループしないことも確認済み（削除はノードを増やさず、`appendData` は `childList` を動かさないため、`MutationObserver` の再入がない）。

修正後は、上の表の3段目・4段目とも **元の場所 1 / 合計 1**、本文の文字列は変化なし。単独の印とリンクの中の印の両方で確認している。

> **残る制約**: 付け直しが起きるのは「走査が走ったとき」（画面遷移か、ノードの追加）である。**属性を変えただけでは走査は起きない。** 監査が必須とした「不可視化のあとに走査の契機がある場合」は直してあるが、属性変化だけの即時追従は費用に見合わないため見送っている。

### RG-6-02 — 要素自身が中身を隠す形を見抜けない（P1）

v1.8.4 は「祖先が `content-visibility:hidden`」の場合を `checkVisibility` で落としていたが、**その要素自身が中身を隠していて、かつ直接テキストを持つ**場合を見落としていた。要素自体は描画されたままなので `checkVisibility` は `true` を返す。

実測（Chrome 151）:

| 反例 | `checkVisibility` | 箱（`offsetWidth`） | v1.8.4 の結果 |
|---|---|---|---|
| `<div style="content-visibility:hidden">commit</div>` | **true** | 740×0 | 見えない側に印・後続は0 |
| `<div hidden="until-found">checks</div>` | true | あり | 見えない側に印・後続は0 |
| `<div hidden>issues</div>` | false | — | すでに正しく除外（対照） |

**直し方。**

1. その要素自身の `getComputedStyle(el).contentVisibility === 'hidden'` を見る（`content-visibility:auto` は落とさない）
2. `[hidden]` を `SKIP` へ追加し、**文字列を取り出す前に**除外する。`hidden="until-found"` も属性があるのでここで落ちる

修正後は4種とも「隠れ側0・後続1」。`content-visibility:auto` の画面外要素が注記されることも維持している（対照）。

### RG-6-03 — プライバシー説明の範囲が、実装より狭い（P1）

実装は、明示的な除外を通した後に文字列を読み、辞書に当たってから可視性を判定する。そのため **`display:none` や `opacity:0` の中の文章も一時的には読んでいる**。`PRIVACY.md` は対象を「表示されている文章」と書いており、実装より狭かった。

**監査の推奨案B（文書を実態へ合わせる）を採用した。** 全テキストノードで先に可視性を測る方式にすると、レイアウト計算が全ノードで走り、ページが目に見えて重くなるためである。

書き換えた内容（日英とも）:

> 除外領域を除いたページの文章を、辞書との照合と可視性の判定のため端末内で一時的に処理する。**CSS で見えなくなっている文章も含まれる。** 印を付けるのは、見えると判定できた一致だけである。候補のテキストは保存・外部送信・第三者共有・人手閲覧をしない。

除外領域（**文字列を取り出す前**に落とすもの）も列挙した: `contenteditable` ／ `textarea` `input` `select` ／ コード表示 ／ `aria-hidden="true"` `.sr-only` `.visually-hidden` ／ `inert` ／ `hidden`（`until-found` を含む）。

`README.md`・`STORE_LISTING.md`・`DESIGN.md` も同じ言い方へ揃えた。Limited Use 準拠の明言、現在 URL の一時利用の開示、保存は真偽値だけ、外部送信なし、PII を意味分類して抽出しない、人手閲覧なし、はそのまま維持している。

**未確定**: Developer Dashboard の実際の定義文は読んでいない（提出者のログインが必要な画面）。3項目（個人を特定できる情報／個人的な通信内容／ウェブ閲覧履歴）は「要確認」のまま、転記欄を用意してある。

### RG-6-04 — 可視性の境界（P2）

**① 見えている `display:contents` の直接テキストを取りこぼしていた。**

原因は測って分かった。**Chrome 151 の `checkVisibility()` は `display:contents` の要素に `false` を返す**（箱を作らないため）。文字は普通に見えている（文字の範囲は矩形を持つ）のに、そこで落としていた。

直し方: `checkVisibility` が false で、かつ `display` が `contents` のときだけ、**箱を持つ最も近い先祖**の可視性で判断し、あわせて**文字の範囲に矩形があること**（`Range.getClientRects()`）を確かめる。

**② 大きな箱に全面の切り取りを掛けた読み上げ専用テキストを拾っていた。** v1.8.4 は「1px 四方以下 ＋ clip」だけを見ていた。大きさに関係なく全面を切り落とす指定（`clip: rect(0 0 0 0)` ／ `clip-path: inset(50%)`）も見るようにした。判定は要素ごとに `WeakMap` で覚え、走査のあいだだけ保持する。

**見送った範囲（既知の制約）**: `transform: scale(0)`、`filter: opacity(0)`、`font-size: 0`、大幅に画面外へ置く配置は、安全に一般化できないため実装していない。**「視覚的に隠された領域をすべて除外する」とは主張しない。** 検出するのは「1px 四方以下＋切り取り」と「全面の切り取り指定」だけである。

### RG-6-05 — 順序の担保を、静的検査から実測へ（P2）

v1.8.4 の担保は `verify.mjs` が `isTarget` の中の文字位置を比べるだけで、別名の変数・補助関数・bracket 記法・分割代入などで迂回できた。

**隔離された世界で、実際に読まれたかを数える E2E を追加した。**

ページ側から `nodeValue` の getter を差し替えても、content script は別の世界で動くため観測できない。そこで **同じ拡張の content script として、本体より先に計測用の `prelude.js` を読み込ませる**。使うのは E2E が並べた一時ディレクトリの manifest だけで、配布物は変えない（`prelude.js` は `tests/` にあり、配布一覧に入っていないことを `verify.mjs` が検査する）。

計装する取り出し口: `Node.prototype.nodeValue` / `textContent`、`CharacterData.prototype.data`、`Text.prototype.wholeText`、`HTMLTextAreaElement.prototype.value`、`HTMLInputElement.prototype.value`。目印の文字列が読まれたら `<html data-rg-reads>` へ記録する。

検査するのは10種類の除外領域（`contenteditable` / `textarea` / `input` / `select` / `pre code` / `.blob-code` / `aria-hidden` / `inert` / `hidden` / `hidden="until-found"`）。**読まれた目印は0件**。対照として、見える場所の目印は必ず読まれることも確かめている（読まれなければ計測そのものが壊れている）。

静的検査は残したが、**補助**であることをコメントと `DESIGN.md` に明記し、「順序を完全に保証する」という表現は撤回した。

### RG-6-07 — 検査が提出物の身元ファイルを書き換えていた（P2）

`package:verify-zip` は「既存の ZIP を検査するだけ」と説明していたが、**検査のときにも身元ファイル（`*.zip.json`）を書き直していた**。CI が作った成果物を別の環境で検証すると、正本に入っている CI の run・commit・環境の記録が、検証した側のローカル情報へ置き換わる。

実測（v1.8.4）: 正本へ CI の `workflowRunId` を書いた後に `package:verify-zip` を実行すると、ファイルのハッシュが変わった。

**直し方。** 作るときだけ正本を書く。検査のときは読んで突き合わせるだけにし、ローカルの記録が要る場合は `*.verified-local.json` という別名へ出す。

検査する項目: ZIP の SHA-256 ／ 中身の合算ハッシュ ／ version ／ 大きさ ／ ファイル数 ／ ファイルの一覧 ／ 出どころのコミットが現在の HEAD と整合するか。**正本が無い場合は失敗**とする（どの実行から出たか分からない ZIP を提出の検証で通さない）。

判別力の確認: 記録を1項目ずつ改ざんして**6種すべてで落ちる**こと、正しい記録なら通ること、正本が無ければ落ちること、を実測した。

## 4. 実装中に気づいたこと

**過去の測定値が、条件によって変わるものだった。** v1.8.4 の記録に「`content-visibility:hidden` の子は `rects=1`」と書いていたが、E2E の実ページで測ると `rects=0`（`offsetWidth` は 740×24 で非ゼロ）だった。**こちらが使っているのは `offsetWidth`/`offsetHeight` なので「箱の検査では判別できない」という結論は変わらない**が、根拠に挙げた数値は文脈依存だった。対照テストの主張を、実際に使っている指標へ書き換えた。

**対照テストが、その食い違いを検出した。** 反例の側を測る試験を持っていなければ、古い数値を根拠にしたまま気づかなかった。
