## 1. 指摘ごとの対応

### RG-7-01 — `display:contents` の可視性を、先祖の1つの答えで代用していた（P1）

**何が起きていたか。** `checkVisibility()` は `display:contents` の要素に **false** を返す。それは「隠れている」ではなく「箱が無い」という意味なのに、v1.8.5 は箱を持つ最も近い先祖へ聞いた1つの答えを子へ転用していた。誤りは**両方向**に出る。

| 形 | v1.8.5 | 正しい答え |
|---|---|---|
| 先祖が `content-visibility:hidden`、中の `display:contents` に語 | 印を付ける | **付けない**（読めない） |
| 先祖が `visibility:hidden`、子が `visibility:visible` に戻している | 落とす | **付ける**（読める） |

**測ってみて分かったこと（監査の反例より条件が狭い）。** `content-visibility:hidden` の中身の `Range.getClientRects()` は、

- **最初から隠れている**場合 → **0 個**（`hasRenderedText` で落ちるので、v1.8.5 でも印は付かない）
- **一度描かれてから隠した**場合 → **隠す前 1 個 / 隠した後も 1 個**（矩形が残り続けるので、`hasRenderedText` では落ちない）

つまり成り立つのは後者だけ。E2E にはその形（`#late-host`）を本命の反例として置き、前者（`#cv-host`）も別に残してある。

**直し方。** 1つの答えを転用せず、性質ごとに聞き分ける（`isVisibleContentsText`）。

| 性質 | 継承 | 聞く相手 |
|---|---|---|
| `visibility` | する | 対象要素自身の computed 値 |
| `display:none` / `opacity` / さらに上の `content-visibility` | しない | 箱を持つ先祖に `checkVisibility({ opacityProperty })`。**`visibilityProperty` はわざと外す** |
| 先祖**自身**の `content-visibility: hidden` | — | 名指しで見る（その先祖は描画されたままなので `checkVisibility` では落ちない） |
| 文字が描かれているか | — | 対象要素の Range |
| 切り取り | — | `isClipHidden` |

**証拠。** E2E「display:contents の文字を、性質ごとに分けて判定する（5種）」「一度描かれてから中身を飛ばされた場所は、矩形が残っていても除外する」。反例が反例であることは、`checkVisibility` と Range の値をブラウザから直接取って対照として固定してある。

### RG-7-02 — 印を片づけるとき、隣にあるものを自分のものと推し量っていた（P1）

**何が起きていたか。** v1.8.5 の `retireGloss` は、片づける時点の `previousSibling` / `nextSibling` を「注記のときに自分が `splitText` で割った対」とみなし、統合していた。DOM は誰でも触れるので、この推し量りは成り立たない。

| 実測した被害 | 測り方 |
|---|---|
| ページ側が印の**後ろ**へ置いた Text node が `isConnected: false` になる | 印の隣へ Text node を挿してから片づけを起こす。`textContent` は同じに見えるので気づきにくい |
| 選択していた一文が `""` になる（`rangeCount` は 1 のまま） | 選択を作ってから片づけを起こす |
| ページ側が印**だけ**を外すと、その語が二度と説明されない | `icon.remove()` → `pushState` ＋ ノード追加 → 印 0 のまま |

**直し方。** 注記した時点で自分が作ったものを控え、それだけを扱う。

```text
{ key, term, icon, parent, termNode, tailNode, splitOffset, placementKind, trigger }
```

守っている不変条件:

- 片づけるときに**現在の隣接から推し量らない**。控えた `termNode` を `handled` から外すだけ
- **割ったものを繋ぎ直さない**（方針B）。繋ぎ直すには節点を1つ消す必要があり、そこに選択範囲やページ側の参照があると壊れる。文字数は割っても変わらないので、割ったままでよい
- ページ側が作った節点を消さない。外すのは自分が入れた `<sup>` だけ
- 印が既に外れていても、記録があるので `handled` を解放できる
- `MutationObserver` で**取り除かれた節点も見る**。自分の印が外れていたら片づけ、その場所をその場で見直す（画面遷移を待たない）
- **用語が末尾ちょうどで終わるときは割らない**。割ると空の節点が1つ増え、往復のたびに増え続ける
- 一致が複数ある節点は**前から順に**処理する。後ろから割ると、先に控えた節点があとの分割でさらに割られ、記録がずれる

**証拠。** E2E 8件（監査が必須とした8つの場面に対応）。

| # | 試験 | 見ているもの |
|---|---|---|
| 1 | 印だけを外されても、その語をもう一度説明できる | 即時復帰と、画面遷移＋全体走査の両方 |
| 2 | 印の**前**へページ側が置いた節点を、消しも書き換えもしない | node の同一性・中身・位置 |
| 3 | 印の**後ろ**へ置いた節点を、消しも書き換えもしない | 同上（v1.8.5 が壊していたのはこちら） |
| 4 | 片づけても選択範囲が壊れない（後ろだけ／跨ぐ／逆向き） | 文字列・anchor / focus の生存・向き |
| 5 | リンクの中の印でも同じ往復ができる | 装飾扱いの印と入口 |
| 6 | 1つの節点に2つの用語があっても、片方だけを正しく戻せる | もう片方が使っている節点の同一性 |
| 7 | 10往復しても、本文・節点の数・印の数が増えも減りもしない | 空の節点が増えないこと |
| 8 | 親ごと差し替えられても、新しい側に1つだけ付く | GitHub の描き直しの対照 |

### RG-7-03 — プライバシー文書が、本文に出た認証情報らしき文字列を落としていた（P1）

**直し方。** 「取得元として触れないもの」と「本文として一時処理し得るもの」を、表の行として分けた（日英とも）。

- 取得元: Cookie（`cookies` 権限なし）・認証 API・`input` / `textarea` / `select`・`contenteditable`
- 本文として一時処理し得るもの: 認証情報らしき文字列・氏名・投稿済みのコメント。**意味のカテゴリとしての抽出はしない**（判定は同梱辞書 61 語との一致だけ）

**証拠。** `scripts/verify.mjs` の否定検査（一括りの断定が戻ってきたら落とす）と、肯定検査（分けて書けていること）。否定検査には**陽性対照**を付けてある——v1.8.5 の書き方を実際に捕まえられることを、同じ実行の中で示す。

### RG-7-04 — legacy `clip` を `position` を見ずに判定していた（P2）

CSS2 の `clip` は絶対配置の要素にしか効かない。v1.8.5 は配置を見ずに `rect(0 0 0 0)` を全面非表示とみなし、**読める文章のほうを除外していた**（実測: `position:static`・幅 1264px の要素の語に印 0）。

いまは `position` が `absolute` / `fixed` のときだけ `clip` を見る。`clip-path` は配置に関係なく効くので位置を問わない。

**証拠。** E2E「legacy clip は絶対配置のときだけ効く（6種）」＝ static 1 / relative 1 / absolute 0 / fixed 0 / `clip-path:inset(50%)` 0 / Primer 1px 0。対照として、同じ `clip` 指定で `position` だけを変えた3つに `elementFromPoint` を当て、static・relative では要素に当たり absolute では当たらないことを見ている（こちらの式の言い換えにしない）。

> 対照を書いたとき、`elementFromPoint` が3つとも `null` を返した。要素が画面の外（y≈2688 / 表示領域 600px）にあり、画面座標で見る API だったため。`scrollIntoView` してから測るよう直し、「画面の中で測れていること」自体も assert に足した。

### RG-7-05 — 動作に必要な最低の Chrome を宣言していなかった（P2）

`manifest.json` に `minimum_chrome_version: "105"` を追加した（`Element.checkVisibility` が入った版）。

**実測（この判断の根拠）。** 同じ拡張の content script として `checkVisibility` を隔離世界から取り除き、8つの場面を比べた。

| 場面 | あり | なし |
|---|---|---|
| 祖先が `content-visibility:hidden` | 隠れた側 0 / 後ろ 1 | **隠れた側 1 / 後ろ 0** |
| 祖先が `opacity:0` | 隠れた側 0 / 後ろ 1 | **隠れた側 1 / 後ろ 0** |
| 祖先が `display:none` | 隠れた側 0 / 後ろ 1 | 隠れた側 0 / 後ろ 1 |
| 残り5場面（`display:contents` 3種・`clip` 2種） | 変化なし | 変化なし |

2つの場面で逆の答えになる。「直接の親だけを見る」程度の代替手段では支えられないので、最低版を書くほうを選んだ。この関係は E2E「checkVisibility が無いと、見えない場所へ印が付く（最低版を要する理由）」として固定してある。

**引数の綴り。** 105〜120 は `checkOpacity` / `checkVisibilityCSS`、121 以降は `opacityProperty` / `visibilityProperty`（Chrome Platform Status のマイルストーンによる）。**両方をまとめて渡している**ので、どちらの版でも効く。Chrome 151 では、旧綴りだけでも新綴りだけでも同じ答えになることを実測した。

> **未実測**: 手元にあるのは Chrome 151 だけで、**105〜150 の実機では試していない**。105 という数字は Chrome Platform Status（`Element.checkVisibility` = 105 / 綴りの追加 = 121）による。実測したのは「この API が無いと何が壊れるか」と「現行 Chrome で旧綴りが効くか」の2つ。
