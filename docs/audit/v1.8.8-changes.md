## 1. 指摘ごとの対応

### RG-9-01 — 印が不可視・無効になっても退役せず、読める同じ語が抑止される（P1）

**何が起きていたか。** 記録が「使えるか」の判定に、DOM の**形**しか使っていなかった。形は整ったまま、意味だけが失われる場面がある。

| 壊し方 | v1.8.7 | v1.8.8 |
|---|---|---|
| 印のある `#h1` を `display:none` にする | 隠れた側に印1・2番目 **0**・ページ全体で branch は1個 | 隠れた側 0・**2番目に1個** |
| 装飾扱いの印の入口（`button`）を `disabled` にする | 押せない入口に印1・後ろの読める語 **0** | 入口 0・**後ろに1個**、旧入口に説明は出ない |

読める語がページに残っているのに、説明がどこにも出ない状態になる。

**直し方。** 判定を2段に分けた。

```text
isCoherent(rec)  … 形だけ。レイアウトを起こさない。毎回の変更で全記録（最大61件）に掛ける
isUsable(rec)    … 見え方・Tab 到達性・入口の意味。レイアウトを起こす。必要なときだけ
```

`reconcileGlosses(deep)` の `deep` を立てるのは、**属性が変わった・文字が書き換わった・ノードが外れた**変更が混ざっているとき、画面遷移のとき、ON へ戻したとき。ノードが増えただけの変更では見え方は変わらないので、安いほうだけを回す。

**見張る対象も足した。** v1.8.7 は `childList` と `subtree` だけだった。

```text
childList: true, subtree: true,
characterData: true,
attributes: true,
attributeFilter: style, class, hidden, inert, aria-hidden, disabled, tabindex,
                 for, href, role, open, contenteditable, id
```

自分が出し入れする吹き出しや、自分が付ける `role` / `tabindex` は数えない（数えると、カーソルを動かすたびに全記録のレイアウト計算が走る）。**選び直しは1回の変更のかたまりにつき最大1回**に制限した。

**証拠。** E2E — 属性の変更だけで2番目へ移ること／入口を無効にすると後ろへ移り旧入口に説明が出ないこと／属性・文字・削除を混ぜた50往復で印が常に0か1で、変更を止めれば数が動かなくなること（単独実行3回で 2.5〜3.1 秒・同時最大1個）。

### RG-9-02 — 語のうしろに文字が増えても「整合している」と誤認する（P1）

**実測（v1.8.7）**: `termNode.appendData('PAGE_SUFFIX')` を実行すると、印は `A rebasePAGE_SUFFIX` の直後に残り、後から現れた本物の `rebase` は **0個**に抑止された。

`isCoherent` は「記録した位置に記録した語がある」ことと「印が語の直後にある」ことは見ていたが、**語がその節点の末尾で終わる**ことを要求していなかった。

**直し方。** 注記した時点では必ず `termNode.length === splitOffset` になっているので、それを不変条件に加えた。

**証拠。** E2E — 追記後に旧記録が退役し、新しい候補へ印が1つだけ付くこと。印の直前が `A rebase` に戻ること。**ページ側が書き足した `PAGE_SUFFIX` はこちらで消さない**ことも同時に確かめている。

### RG-9-03 — `label` の対応先が変わっても、古い入口を保持する（P1）

**実測（v1.8.7）**: `label.htmlFor` を `ia` から `ib` へ変えると、`label.control` は `ib` になるのに、説明の入口は `ia` のままだった。**新しい入力欄にフォーカスしても説明が出ず、古い入力欄のほうに出た。**

記録は「入口が DOM にあるか」と「印が指す ID と一致するか」しか見ておらず、**その場所からいま解決される入口**を計算し直していなかった。

**直し方。** `isUsable` で `resolvePlacement(rec.parent)` を解き直し、`kind` と `trigger` の同一性を要求する。`label` の場合、`resolveTrigger` が `host.control` を見るので、これは `label.control === rec.trigger` を要求することと同じになる。

あわせて、**その入口を指す記録が1つも無くなったら目印を外す**ようにした（`releaseTriggerIfUnused`）。残したままだと、入口でなくなった要素に目印だけが残る。

**証拠。** E2E — `for` を変えたあと、新しい入力欄だけに説明が出る／古い入力欄には説明も残留した目印も無い／`label` の印は1つのまま／後ろの候補へ余計に増えない。

### RG-9-04 — 保護領域へ移ったあとの本文を、除外判定より前に読む（P1）

**何が起きていたか。** `isTarget` は走査の入口で `closest(SKIP)` を先に見る。ところが記録の整合を確かめる `isCoherent` は、**現在の親が編集領域などへ変わっていないかを見ずに** `rec.termNode.nodeValue` を読んでいた。

**実測（v1.8.7）**: 隔離世界で `Node.prototype.nodeValue` の getter を包んだうえで、注記済みの段落を `contenteditable=true` にし、本文を `RGSENTINEL_PRIVATE branch` に変えて無関係なノードを1つ足すと、**`RGSENTINEL_PRIVATE` が記録された**（変更前は0件）。

これは公開している説明（「触れない領域は、値そのものを取り出さない」）と実装が食い違う状態であり、ストア申告と Limited Use の整合に関わる。

**直し方。** `isCoherent` の先頭で、**文字に触れる前に** `rec.parent.closest(SKIP)` を見る。保護領域なら本文を読まずに記録を退役させる。退役すると、その語はふつうの候補として後ろの出現へ回る。

**計測の方法も足した。** `matcher-tap.js` は「辞書の照合まで届いたか」を測る道具で、**照合せずに読むだけの経路はそこに映らない**。そこで `tests/e2e/nodevalue-probe.js` を新設し、`nodeValue` / `data` / `textContent` / `substringData` の4つを隔離世界で包んで、読み取りそのものを数える。

> **陽性対照を同じ実行に入れてある。** 計装した直後に、detached な Text node から `RGSENTINEL_SELFTEST` を1回読む。これが記録されていなければ「読まれていない」は計測の失敗と区別が付かない。判定は「記録がこの1件だけであること」で行う。

**証拠。** E2E 4件（`contenteditable` / `aria-hidden` / `inert` / `hidden`）— いずれも sentinel の読み取りが0件で、印が退役し、**本文は1文字も変わっていない**。加えて、保護領域から戻したら通常の候補として選び直せること。

`scripts/verify.mjs` にも、`isTarget` と `isCoherent` の**両方**について「SKIP 判定より前に値を読んでいない」検査を置いた（単純な後戻りを早く止めるため。本命は上の E2E）。

### RG-9-05 — 所有の判定が class と属性の値に依存する（P2）

**実測（v1.8.7）**、ページ側が同じ名前を使っているだけで4つの被害が出た。

| ページ側がしたこと | v1.8.7 の結果 |
|---|---|
| `class="iiyaku-icon"` のリンクを後から足す | **消された** |
| そのリンクを押す | `defaultPrevented=true` になり、リンク先へ移動しなかった |
| 2つのリンクに同じ `data-iiyaku-trigger="shared"` を置く | どちらの入口でも**2件**（milestone と wiki）が集約表示された |
| 値に `"` と `]` を入れる | その値で組んだ selector が `SyntaxError` |

**直し方。**

- 印と入口の結び付きは `WeakMap` / `WeakSet` の**内部の表**だけで持つ。ページ DOM の属性は読まない
- 自分が作った印に、読み込みごとに変わる合言葉（`data-iiyaku-owner`）を入れる。**合言葉があって、かつ自分が作ったものではない**ものだけを複製として取り除く
- 当たり判定は `ownedIconAt()`（自分が作った印まで祖先をたどる）に統一。`closest('.iiyaku-icon')` は使わない
- 入口の目印は `data-iiyaku-entrance` へ改名し、**書くだけで読まない**。既に同じ名前の属性があれば上書きしない
- 外から来た値を CSS selector へ埋めない

**証拠。** E2E — ページ所有の `.iiyaku-icon` が読み込みの前後どちらでも残る／そのリンクのクリックが横取りされず `location.hash` が変わる／同じ `data-iiyaku-trigger` を持つ2つの入口でそれぞれ1件だけ出る／目印の値がすべて自分の合言葉つきで重複が無い／ページ側の属性が書き換わっていない／`bad"]sel` を持つ入口でも説明が出る。

### RG-9-06 — `characterData` を監視していない（P2）

**実測（v1.8.7）**: 印の直前の Text node を `A banana` に書き換えた**直後**は、印が `A banana` の後ろに残り、2番目の候補は0個。無関係なノードを1つ足して初めて移動した。

**直し方。** `characterData: true` を足した。あわせて、**文字が変わった場所と属性が変わった場所を走査し直す**ようにした。増えたノードだけを見ていると、「触れない領域から戻った」「隠れていたものが見えるようになった」場所が取り残される（実測で、保護領域から戻した段落に印が付かなかった）。文字が変わった節点については、前に「見なくてよい」と決めた記録も消す。

**証拠。** E2E — 書き換えたあと、他の DOM 変更を待たずに2番目へ移ること。

### RG-9-07 — 面積0の `clip-path` を複数取りこぼす（P2）

v1.8.7 は `inset()` の値が**すべて百分率**のときしか判定しなかった。ところがブラウザが返す値は `inset(50% 0 50% 0)` と書いただけで `inset(50% 0px)` になる。長さと百分率が混ざった瞬間に判定を降りていた。

| 書き方 | computed 値 | v1.8.7（隠れた側/後ろ） | v1.8.8 |
|---|---|---|---|
| `inset(50% 0 50% 0)` | `inset(50% 0px)` | **1 / 0** | 0 / 1 |
| 100×100 の箱へ `inset(50px)` | `inset(50px)` | **1 / 0** | 0 / 1 |
| `inset(0 100% 0 0)` | `inset(0px 100% 0px 0px)` | **1 / 0** | 0 / 1 |
| `circle(0)` | `circle(0px)` | **1 / 0** | 0 / 1 |
| `inset(10%)` | `inset(10%)` | 1 / 0（正しい） | 1 / 0 |
| `display:contents` 自身の `inset(50%)` | — | 効かせない（正しい） | 効かせない |

**直し方。** border box の寸法（`offsetWidth` / `offsetHeight`）へ換算し、`top + bottom >= 高さ` か `left + right >= 幅` なら面積0とする。寸法が取れないときは百分率だけで言えることに限る。`circle()` と `ellipse()` は半径が0なら面積0。

**既知の制約（断定しない側へ倒す）**: `calc()` を含む値、`polygon()`、`path()`、`shape()` は解かない。値だけからは面積を決められないため、**可視として扱う**。したがって `clip-path: inset(calc(50% + 1px))` で隠された語は、いまも「ページで最初の1回」を消費する（実測で確認済みの、残っている穴）。

**証拠。** E2E — 面積0の4形すべてで「隠れた側0・後ろ1」。落としすぎの対照として、`inset(10%)` と `display:contents` 自身の `inset(50%)` は可視のまま扱うこと。

### RG-9-08 — 監査入口が名乗る検査件数が古い（P2）

**実測**: `AUDIT.md` は §10 で「158項目」、§4-1 で「166項目」と名乗っていたが、`main` の実際は **175項目**だった。版・SHA・タグは検査していたのに、**件数だけが同期の対象外**だった。

**直し方。** 件数を人が書き写す限り必ずずれるので、**verify 自身の最終件数と文書の記載を突き合わせる検査**を足した。この検査自身が最後の1件なので、いまの件数に1を足したものが最終の件数になる。

**証拠。** この検査を入れた時点で、`158, 166 / 実際: 194`（その後の追加で 196 になっています） として不一致を報告した（＝実際に効いている）。

## 4. 途中で作った後退と、その是正

**後退を2つ作り、どちらも実測してから直しました。**

**① 入口の解き直しを、語が見つかるたびに走らせていた。** `usableGloss` は「その語はもう説明済みか」の判定として `matcher.findHits` から**一致ごとに**呼ばれます。そこへ `resolvePlacement`（`closest` ＋ 描画確認）を素で入れたため、用語の多いページで **24.2ms → 33.7ms（10組すべてで遅い）** になりました。走査1回のあいだに記録の見え方は変わらないので、`isUsable` の結果を走査ごとの `WeakMap` へ覚えるようにしました。

**② 記録ごとに除外判定（`closest(SKIP)`）を呼び足していた。** ①を直したあと、順序を入れ替えた対照で **+1.4 ms / +3.4 ms（16組中14組で遅い）** が残りました。`SKIP` は25個ほどの選択子を持つので、記録61件 × 一致ごとに呼ぶと積み上がります。除外領域かどうかは走査1回のあいだ変わらない（こちらが入れるのは空の `<sup>` だけで、本文の祖先にはならない）ので、要素ごとに覚えるようにしました。これは `isTarget` にも効くため、最終的には v1.8.7 より速くなっています。

> **②は、静かな状態で測り直すまで「差は0」と読み違えていました。** 最初の計測は SD が 3.7〜5.2 ms あり、+1.4 ms を見分ける分解能がありませんでした。**平均が動かないことを「効いていない」の根拠にせず、ばらつきを見る**必要があります。

## 5. 性能

用語の多いページの写しを使い、v1.8.7 と**交互に**測りました（ページの中で計測。大きな領域を差し込んだときの1バッチ分で、初期走査と同じ経路を通ります）。

| 順序 | v1.8.7 中央値 | v1.8.8 中央値 | 組ごとの差の中央値 | v1.8.8 が遅かった組 |
|---|---:|---:|---:|---:|
| v1.8.7 が先 | 26.9 ms（SD 7.3） | **21.6 ms**（SD 2.7） | **−2.4 ms** | 2 / 8 |
| v1.8.8 が先 | 23.1 ms（SD 3.1） | **22.0 ms**（SD 1.7） | **−2.6 ms** | 0 / 8 |

**合計16組のうち、v1.8.8 が遅かったのは2組。両方の順序で差の向きが同じ**なので、順序の偏りではありません。

退役と選び直しの費用は、属性・文字・削除を混ぜた**50往復で 2.5〜3.1 秒**（単独実行3回：3,145 / 2,529 / 2,654 ms。各往復に 40ms の待ちを入れているので、処理そのものは十分に軽い）。同時に存在する印は常に **0 か 1** で、変更を止めると数が動かなくなります。
